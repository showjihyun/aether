## 424초를 TTFSA 로 읽으면 틀립니다

숫자가 문서의 10분 목표 안에 들어왔지만, **가장 비싼 두 자리가 이 머신에서 이미 더워져 있었습니다.** 그 사실을 적지 않으면 이 기록이 조건을 바꿔 숫자를 맞춘 것이 됩니다(EI-3).

| 왜 낙관적인가 | 근거 |
| --- | --- |
| **1절의 clone 이 없었습니다** | 에이전트는 있는 체크아웃을 받았습니다. 처음 보는 사람은 `git clone` 과 **찬** `uv sync` 를 냅니다 — 60여 패키지가 18초면 캐시 적중이고 다운로드가 아닙니다 |
| **4절의 빌드가 더웠습니다** | `up --build` 가 136초였습니다. 문서 자신이 "빌드 캐시가 없는 머신에서는 이 단계가 이 문서에서 가장 긴 구간입니다" 라고 적는데 **이 실행에서는 가장 길지 않았습니다** — 즉 문서가 말하는 그 찬 머신의 숫자가 아닙니다 |
| 6절 64초는 저장소 마찰이 아닙니다 | 그중 **60.4초가 CPU 위 ollama 의 추론**입니다(192 토큰). CLI·API 왕복은 약 3초입니다 |

**찬 머신의 숫자는 여전히 없습니다.** 그리고 사람이 헤맨 시간은 이 방법으로 영원히 얻을 수 없습니다.

### F-10 — 그리고 2026-10-20 의 제 검증이 틀렸습니다

문서의 정리 명령은 compose 파일을 **하나만** 이름 부릅니다(`compose.yaml`). 4절은 **둘로** 띄웁니다. 글자 그대로 따른 결과: `aether-dev-llm-1` 이 `Up (healthy)` 로 남고, `aether-dev_ollama_models`(397 MB)가 남고, 네트워크는 `Resource is still in use` 로 못 지웁니다. 그래서 바로 다음 문장 — "`-v` 가 볼륨(**모델 포함**)까지 지웁니다" — 은 **적힌 대로는 거짓입니다.** 지우겠다고 특정한 그 볼륨이 정확히 손이 닿지 않는 볼륨입니다.

원인을 기계로 확인했습니다:

```
$ docker compose -p aether-probe -f infra/docker/compose.yaml config --services
api migrate otel-collector postgres redis web worker          # llm 이 없습니다

$ docker compose -p aether-probe -f infra/docker/compose.yaml -f infra/docker/compose.llm.yaml config --services
api llm migrate otel-collector postgres redis web worker
```

`llm` 서비스는 `compose.yaml` 173행에 있지만 `profiles: ["llm"]` 뒤에 있고, 그 프로파일을 벗기는 것은 `compose.llm.yaml` 15행의 `profiles: !reset []` 입니다. 그래서 단독 파일로 부른 `down -v` 는 `llm` 을 **자기 서비스로 보지 않고**, 살아 있는 그 컨테이너가 볼륨과 네트워크를 붙듭니다.

**[1회차 기록](ttfsa-agent-dryrun-2026-10-20.md)의 「에이전트가 틀린 것」 표 둘째 행을 철회합니다.** 그때 1회차 에이전트가 "정리 절이 `compose.yaml` 하나만 써서 llm 자원을 못 지운다" 고 보고했고, 저는 *"**틀렸습니다.** `ollama_models` 는 오버레이가 아니라 `compose.yaml` 203~206행에 정의돼 있어 `down -v` 가 지웁니다"* 로 반박했습니다. **볼륨의 정의 위치는 맞았지만 결론이 틀렸습니다** — 중요한 것은 볼륨이 어디에 선언되었는지가 아니라 **그것을 쥔 컨테이너가 멈추는지**입니다. 1회차 에이전트의 보고가 맞았고 제 반박이 틀렸습니다. 넉 달 뒤에 같은 자리를 다시 재면서 알게 된 것이고, 그 사이 이 기록은 틀린 반박을 사실로 들고 있었습니다.

### F-11 — F-7 수정이 반쪽이었습니다

4절 확인 2번은 `docker compose … ps` 입니다(`-a` 없음). 그 아래 주석은 "2번 출력에서 `migrate` 가 `Exited (0)` 인 것은 **정상**입니다" 와 "`worker` 가 `Exited` 면 비정상" 을 적습니다. **종료된 컨테이너는 `-a` 없이 나오지 않습니다.** 실측의 `ps` 는 일곱 행(api·llm·otel-collector·postgres·redis·web·worker)만 냈고 `migrate` 행은 **없었습니다.**

읽는 사람은 **있을 수 없는 줄을 찾으라는 지시**를 받고, 자연스러운 결론은 "migrate 가 안 돌았다" 입니다 — 정확히 반대의 경보입니다. F-7 은 "migrate 가 일회성이라는 말이 없다" 였고 2026-10-20 에 그 문장을 더해 닫았는데, **더한 문장이 그 명령이 내지 않는 출력을 설명하고 있었습니다.** 고친 것이 작동하는지 보지 않고 닫은 자리입니다.

### F-12 — `echo $?` 는 직전 명령의 것입니다

4절은 `up` 을 한 펜스 블록에 적고 산문을 하나 끼운 뒤 **다른 블록**에 확인 셋을 적으며 그 첫 줄이 `echo $?` 입니다. `ps` 를 먼저 돌린 사람, 스크롤한 사람, 프롬프트 훅이 끼어든 셸은 **다른 명령의 상태**를 읽습니다. 확인 셋을 셋으로 둔 것은 F-2 의 수정이므로 줄이지 않고, 종료 코드를 `up` 과 같은 줄로 옮깁니다.

## 문구만 고치는 여섯 건

테스트로 고정할 계약이 아니라 명료성입니다. 실측에서 읽는 사람이 **추측해야 했던** 자리들입니다.

| 어디 | 무엇을 추측해야 했는가 |
| --- | --- |
| 2절 `AETHER_MODEL_API_KEY` | "빈 값" 이 dotenv 에서 셋으로 읽힙니다 — 줄 삭제 / `KEY=` / `KEY=""`. `KEY=` 를 골라 작동했습니다 |
| 0절 "다른 난수 생성기를 쓰셔도 됩니다" | `openssl rand -base64 24` 를 쓰면 `+` `/` `=` 가 dotenv 값에 들어갑니다 |
| 5절 `export AETHER_API_KEY=…` | 비밀값이 셸 히스토리에 남습니다 — 이 저장소의 비밀값 규칙과 어긋납니다 |
| 6절 `agent create` + `run <위에서 출력된 id>` | 한 블록이라 붙여넣기처럼 보이는데 아닙니다. 설명이 블록 **뒤에** 옵니다 |
| 6절 답의 품질 | 0.5b 모델이 뜻이 통하지 않는 한국어를 냅니다. 문서가 모델은 말하지만 **출력이 엉성할 것이라는 말을 하지 않습니다** — 고장으로 의심할 수 있습니다 |
| 5절 → 6절 | **같은 셸이어야 합니다**(키는 한 번만 보입니다). 문서가 그 말을 하지 않습니다 |

## 고치지 않은 것

- **`qwen3.8:27b`** — 에이전트가 "실재하지 않아 보이는 태그" 로 올렸습니다. 확인했습니다: `compose.yaml` 114행 · `.env.example` 44행 · `fetch-model.sh` 24행 · `apps/worker/.../settings.py` 69행과 그 테스트까지 **저장소 전체의 제품 기본값**입니다. 문서 버그가 아니므로 건드리지 않습니다.
- **7절(화면 보기)과 「제품 모델로 바꾸기」** — 이번 실행이 밟지 않았습니다(문서가 7절을 선택으로 표시하고 6절에서 시계를 멈추라고 합니다). 측정하지 않은 자리는 고치지 않습니다.
- **F-3 의 제품 절반**(worker 가 없을 때 `aether run` 의 무한 대기) — 이번 실행에서는 **재현되지 않았습니다.** worker 가 정상이었으므로 그 경로를 지나지 않았고, 따라서 6절 증상 표의 그 줄은 **여전히 검증되지 않은 채**입니다. 보류 상태 그대로입니다.

## 이 수정 뒤에 H-4 를 재는 사람에게

**또 "수정 뒤" 의 문서를 보게 됩니다** — 1회차 뒤 F-1 ~ F-9 가 그랬고, 이번 뒤 F-10 ~ F-12 가 그렇습니다. 그 사실을 그 사람의 기록에 적어야 합니다(EI-3). 돌을 치우는 것 자체는 옳습니다 — **처음 보는 사람은 한 번만 처음**이고, 아는 돌을 깔아 두고 사람을 보내면 그 사람이 돌려주는 것이 이미 적어 둔 목록이 됩니다. 다만 치운 뒤의 숫자를 치우기 전의 목표와 비교하지 않습니다.

## 이 기록이 하지 않는 주장

- "TTFSA 가 7분 04초입니다" — **아닙니다.** clone 과 빌드 캐시가 더웠고, 사람이 헤맨 시간이 0 으로 들어가 있습니다.
- "R-12 가 참입니다" — **절반만입니다.** 이 기록이 쓰인 날에는 "아닙니다" 였고, **2026-10-25 에 spec 0006 개정 9(D-22)** 가 R-12 를 쪼갠 뒤 이 기록은 **R-12a**(문서 그대로 따라 첫 Run 이 `succeeded`)의 근거가 되었습니다. **R-12b**(TTFSA 10분)는 여전히 **아닙니다** — 그것은 처음 보는 **사람**의 기록이 커밋될 때 참이 되고, backlog **H-4** 가 그 자리입니다. 이 문서는 시간 숫자를 제공하지 않습니다.
- "Quickstart 에 마찰이 없습니다" — **아닙니다.** 완주했다는 것과 매끄러웠다는 것은 다릅니다. 위에 아홉 자리를 적었습니다.
