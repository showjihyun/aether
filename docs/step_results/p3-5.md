# P3-5 — KPI 계측 (Task Success / Context Token)

Context Compiler 가 내놓는 숫자가 처음으로 **밖에서 보입니다**. P3-1 이 만든 `ContextReport` 는 그동안 Compiler 와 Executor 사이에서만 오갔습니다.

## 무엇이 생겼는가

- `Tracer` 포트에 **`set_attributes(Mapping[str, str])`** — 세 구현(`OtelTracer`·`NoopTracer`·테스트의 `InMemoryTracer`)이 모두 따릅니다.
- `model.benchmark` 가 아니라 **`model.complete` span 마다** Context 숫자: `context.tokens.<source>`(실제로 있던 소스만), `context.tokens.total`·`context.budget`(항상), `context.dropped.<source>`(뺀 소스만), `context.dropped.sources`(뺀 순서 그대로 `,` 로 이은 것).
- `run` span 에 **`aether.run.status`** — `succeeded`·`failed`·`cancelled`·`timed_out`. Task Success 의 원천입니다.
- `scripts/smoke.sh` 가 trace 안에 `context.tokens.total` 속성이 **실제로 나타나는지** 확인합니다 — "trace 가 없다" 와 "trace 는 있는데 속성이 없다" 는 다른 실패 메시지입니다.
- 새 문서 [../observability.md](../observability.md) — span·속성 표, 실행해서 출력까지 확인한 집계 예시, 그리고 "이 숫자를 단일 목표로 주지 않는다" 한 절.
- 후보 `2026-10-10-002` — pgvector 교체 비용(이미지 +226 MB)이 교체한 단위에서 측정되지 않았습니다.

## 왜 그렇게 했는가

- **포트를 늘렸습니다.** 지금 `Tracer.span(name, attributes)` 는 span 을 **열 때만** 속성을 받는데, 이 단위가 올려야 하는 두 값은 열린 **뒤에** 압니다 — Context 숫자는 `compile()` 이 돌아온 뒤(이미 `model.complete` span 안), 종결 상태는 `_finalize` 뒤(`run` span 은 훨씬 앞에서 열림). 포트를 늘리지 않으면 계측을 위해 span 배치를 비틀어야 하고, **계측이 실행 구조를 바꾸면 그 계측은 관측이 아닙니다.**
- **없는 소스에 `"0"` 을 채우지 않습니다.** 속성이 없는 것은 "그 소스가 애초에 없었다", `"0"` 은 "있었고 비용이 0이었다" 입니다. 둘을 같은 값으로 적으면 집계가 조용히 거짓말을 합니다 — 테스트 1건이 이 구분을 고정합니다.
- **집계 예시를 SQL 로 쓰지 않았습니다.** 이 저장소에 span 을 담는 표가 **없습니다**. 있는 것은 collector 가 내보낸 `infra/docker/out/otel-smoke/spans.jsonl` 뿐이라 `jq` 로 썼고, **실제 파일에 돌려 출력을 문서에 붙였습니다**. 없는 표에 대한 SQL 을 적는 것은 허구를 문서화하는 것이고, 허구는 처음 쓰려는 사람에게서 깨집니다.
- **속성 값은 전부 문자열입니다.** 포트의 기존 계약(spec 0002 2.9)을 이 단위 때문에 바꾸지 않았습니다. 대가는 집계에서 `tonumber` 가 필요한 것이고, 그 대가가 쌉니다.
- **본문은 어떤 속성에도 넣지 않습니다**(D-11). system prompt·입력·응답을 알아볼 수 있는 문자열로 심고 그것이 어느 속성 값에도 없음을 단언하는 테스트로 고정했습니다.

## 정한 것과 다른 점

- **`Tracer` 포트를 늘린 것은 plan 에 없습니다.** plan 은 "`ContextReport` 의 숫자를 span 속성으로" 라고만 적고 그 경로를 정하지 않았습니다. 위의 이유로 제가 정했습니다.
- **plan 의 "집계 쿼리 하나" 를 `jq` 로 해석했습니다.** span 저장소가 없기 때문입니다. 장래에 생기면 같은 집계의 SQL 을 그 문서에 더합니다.
- **`jq` 실행 파일이 이 개발 환경에 없습니다.** 같은 jq 프로그램을 libjq 바인딩(PyPI `jq`)으로 실제 파일에 돌렸습니다 — 프로그램은 검증됐고 CLI 호출 한 줄만 미확인입니다. 문서가 그 사실을 적습니다.
- **집계 예시를 리뷰에서 고쳤습니다.** 구현자의 판이 `model.complete` 가 없는 Run — 시작 전에 취소된 Run — 이 파일에 하나라도 있으면 **집계 전체가 죽었습니다**(`null (null) and number (0) cannot be divided`). 그 Run 을 하나 섞어 실패를 재현한 뒤 `// 0` 과 0 나눗셈 가드를 넣고 다시 확인했습니다. 문서의 예시는 **처음 쓰려는 사람의 데이터에서 깨지지 않아야** 합니다.
- **문서의 재시도 서술도 고쳤습니다.** 모델 재시도는 span 을 더 만들지 않고 같은 `model.complete` 안에서 `compile` 을 다시 해 속성을 **덮어씁니다** — 재시도한 호출의 속성은 마지막 시도의 조립입니다. 시도별 조립을 보려면 span 을 시도마다 열어야 하고, 이 단위는 하지 않았습니다.
- **구현 전에 통과한 테스트 둘**을 보고가 적었습니다. 본문 미노출은 속성이 아예 없어 자명하게 통과했고(변이 주입으로 무력하지 않음을 확인), `InMemoryTracer` 의 병합 테스트는 fake 를 먼저 만들어 통과했습니다(fake 의 의미를 고정하는 용도, 변이 없음).

- **이미지 크기 실측**: `pgvector/pgvector:pg16` 디스크 621 MB / 압축 156,098,403 B, 교체 전 `postgres:16-alpine` 395 MB / 109,995,527 B — **+226 MB(+57%)**. Air-Gapped 가 제품 요구이므로 이 숫자는 제품에 걸립니다. 후보 `2026-10-10-002` 가 "기록만 하고 임계값은 사람이" 를 제안합니다. 로컬 이미지의 digest 가 compose 의 고정 sha256 과 같은지는 확인하지 않았습니다.
