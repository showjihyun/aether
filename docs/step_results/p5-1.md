# P5-1 — 노드 실행 투영 (worker 통지 → api 적용)

Workflow Run 의 **노드 단위 상태가 `control` 에 생겼습니다.** 화면이 가리킬 수 있는 첫 데이터이고, 이 단위의 전부는 "api 역할이 `data` 를 보지 않고도 노드 상태를 안다"(spec 0007 R-5) 하나입니다. 조회 경로와 SDK 는 P5-2, 화면은 P5-3 입니다.

PR [#186](https://github.com/showjihyun/aether/pull/186).

## 무엇이 생겼는가

- **마이그레이션 0012** — `control.workflow_node_states`. PK `(workflow_run_id, node_id)`, 열은 `kind`·`status`·`status_seq`·`started_at`·`finished_at`·`failure_reason`. `status` 는 `text` + `CHECK` 여섯 값(`ck_workflow_node_states_status`). GRANT 는 `aether_control` 에만 — **`aether_data` 에는 0건**이고 `data` 권한 추가도 0건입니다.
- **worker 의 통지** — `aether:workflow_node_states:status` 스트림(`packages/workflow/.../ports/outbound/workflow_node_status_notifier.py` + `adapters/outbound/redis/...`). `advance_workflow_run.py` 가 `node.started`·`node.finished` 발행 뒤, 그리고 `WAITING_APPROVAL`·`WAITING_RUN` 파킹에서 부릅니다. 값 없는 선택 필드는 **키 자체를 보내지 않습니다**.
- **api 의 소비자** — `adapters/inbound/stream/workflow_node_status_consumer.py`(group `aether-api`, 자기 PEL 먼저, 독약 메시지는 WARNING 과 함께 ack), 유스케이스 `apply_workflow_node_status.py`, 메시지 `domain/workflow_node_status_message.py`(`extra="ignore"`).
- **투영 한 문장** — `adapters/outbound/db/workflow_node_state_projection_store.py` 의 `INSERT … SELECT … FROM control.workflow_runs … ON CONFLICT (workflow_run_id, node_id) DO UPDATE … WHERE t.status_seq < excluded.status_seq`. 없는 Run 이면 행도 FK 예외도 없고, `started_at` 만 `COALESCE(new, old)` 입니다.
- **배선** — `apps/worker/.../main.py` 가 `node_notifier` 를 넘기고, `apps/api/src/aether_api/main.py` 의 lifespan 이 소비자 스레드를 띄웁니다. 스트림 이름은 `settings.workflow_node_status_stream`.
- 문서 — [data-model.md](../data-model.md)(표 절 + 마이그레이션 0012)·[api.md](../api.md) 6절은 **P5-2 의 PR** 에서 함께 적었습니다(투영이 읽히는 자리가 그때 생깁니다).

## 왜 그렇게 했는가

- **쓰는 주체는 worker 가 아니라 api 입니다.** 착수 전 실측에서 `aether_data` 가 `control` 에 **SELECT 뿐**인 것을 다시 확인했습니다(마이그레이션 0001·0005). intent 0007 의 열린 질문에 제가 제안한 답은 "worker 가 직접 쓴다" 였고 **그것이 틀렸습니다** — 선례 셋(`aether:runs:status`·`aether:knowledge:ingestions:status`·`aether:workflow_runs:status`)이 모두 통지→투영입니다. GRANT 를 넓히는 쪽은 권한 변경이라 사람 검토 대상이고, 그 길을 가지 않았습니다(spec 0007 D-3).
- **노드 출력은 투영에도 통지에도 넣지 않았습니다**(D-4). spec 0005 D-8 이 "출력의 소비자가 둘로 늘어나면 그 PR 이 결정을 다시 연다" 고 적었고, 상태만 보내면 그 문을 열지 않습니다. `tests/arch/test_workflow_output_stays_in_data.py` 가 **그대로 통과**합니다.
- **표 이름을 `node_states` 로 바꿨습니다.** spec 초안의 `control.workflow_node_executions` 는 정본(`data.workflow_node_executions`)과 **같은 이름을 두 평면에** 만들고, 그것을 지키던 구조 테스트가 먼저 발화했습니다. 테스트를 좁히는 선택지가 있었지만 택하지 않았습니다 — 그 판정이 지키는 것이 "어느 평면의 표인지 코드에서 읽힌다" 이고, 이 표에는 상태만 있어 새 이름이 사실에 더 가깝습니다(spec 0007 **개정 1**).
- **`status` 를 enum 으로 만들지 않았습니다.** `aether_control` 에 `data` 스키마 USAGE 가 없어 정본의 enum 을 쓸 수 없고, `control` 에 새 enum 을 두면 "workflow enum 은 둘" 이라는 기존 불변식(`test_workflow_run_executions_integration.py`)이 깨집니다. `text` + CHECK 로 값 여섯을 손으로 맞췄습니다.
- **키가 `(run, node)` 라 `status_seq` 비교도 노드 단위입니다.** Run 수열을 그대로 쓰므로 늦게 도착한 같은 노드의 메시지만 버려지고, 다른 노드의 전진은 서로를 막지 않습니다.

## 정한 것과 다른 점

- **표와 스트림의 이름**이 spec 초안과 다릅니다 — 위의 세 번째 항목. spec 0007 **개정 1 [편집]** 으로 기록했고 요구사항의 뜻은 그대로입니다.
- **`status` 의 타입**이 "정본과 같은 enum" 에서 `text` + CHECK 로 바뀌었습니다 — 같은 개정의 두 번째 항목.
- 그 둘 말고는 plan 0007 2절의 P5-1 표와 같습니다. 마이그레이션 하나, 통지 하나, 소비자 하나입니다.

## 남긴 것

- **조회 경로와 SDK 는 P5-2**, 화면은 **P5-3** 입니다. 투영은 이 단위에서 **아무도 읽지 않습니다** — 그래서 [data-model.md](../data-model.md)·[api.md](../api.md) 의 문서도 P5-2 의 PR 에 넣었습니다.
- **`LOOP` 의 회차별 이력은 투영에 없습니다.** 노드당 한 행이고 회차는 정본(`data.workflow_node_executions.iteration`)에만 있습니다. 화면이 회차를 보여야 한다는 요구가 오면 그때 결정이 다시 열립니다.
- **SSE(`aether:workflow_runs:{id}:events`)는 여전히 읽는 경로가 없습니다.** spec 0007 의 범위가 아닙니다.
