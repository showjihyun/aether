# P3-2b — Knowledge 적재 파이프라인 (PR #120)

선언과 적재를 끝에서 끝까지 이었습니다. api 가 **선언**하고 worker 가 **실행**합니다 — Run 과 같은 모양입니다(D-4).

## 무엇이 생겼는가

- HTTP: `POST /knowledge-sets`(선언) · `POST /knowledge-sets/{id}/ingestions`(적재 요청) · `GET /knowledge-sets/{id}/ingestions/{id}`(상태).
- `packages/context`: `Connector`(Filesystem) · `Indexer`(문자 기준 고정 크기 + 겹침, 기본 1000/200) · `Embedder` · `KnowledgeStore`(pgvector) 포트와 어댑터, 그리고 적재 유스케이스.
- 스트림 **둘**: `aether:knowledge:ingestions:requested`(api → worker) 와 `aether:knowledge:ingestions:status`(worker → api).
- `docs/api.md` 7절(Knowledge 적재)과 6절의 스트림 두 줄.

## 왜 그렇게 했는가

- **상태를 쓰는 주체는 api 뿐입니다**(spec 개정 5). `aether_data` 는 `control.knowledge_ingestions` 에 **SELECT 만** 가집니다(P3-2a 의 GRANT 방향). 그래서 worker 는 상태를 직접 쓰지 못하고 상태 스트림으로 api 에 되돌려 보냅니다 — Run 의 `aether:runs:status` 와 같은 모양입니다. 권한을 넓혀 worker 가 직접 쓰게 하는 쪽을 고르지 않았습니다. GRANT 방향이 Plane 경계의 근거입니다.
- **임베딩은 `Embedder` 포트를 지납니다** — `aether_context` 가 `aether_runtime` 을 import 하지 않습니다(AR-3). gateway 를 꽂는 조립은 worker 의 `main` 에서만 합니다.
- **재적재는 교체입니다**(append-only 가 아닙니다) — 같은 Knowledge Set 의 기존 청크를 전부 지우고 새로 넣습니다. 적재는 감사가 아니라 파생 데이터입니다.

## 반려 1회와 그 뒤에 일어난 일

테스트가 구현 뒤에 쓰여 **red 증거가 없어 반려**했습니다. 다시 쓰게 하는 대신 단언 8건에 **변이 주입 증거**를 요구했습니다 — 제품 코드를 한 줄 틀리게 바꿨을 때 그 테스트가 실패하는지. 10건의 변이가 전부 잡혔지만, 중요한 것은 변이가 **잡지 못한 것**이었습니다.

| 변이가 드러낸 것 | 그래서 무엇을 했는가 |
| --- | --- |
| `test_list_documents_is_deterministic_across_repeats` 가 순서 불안정을 잡지 못함 — 같은 프로세스에서 `hash()` 가 안정적이기 때문 | 반복 횟수로 덮을 수 없는 부류이므로 구조 테스트(P3-1 에서 만든 것)가 그 자리를 맡습니다 |
| `IngestionStatusConsumer` 를 Redis 위에서 검증하는 테스트가 **전혀 없었고**, worker 에서 api 로의 상태 왕복을 실제 worker 어댑터까지 포함해 거치는 테스트도 없었음 | 두 경로 모두 테스트를 추가했습니다 |

"변이가 잡혔다" 만으로 통과시키지 않은 것이 이 단위의 교훈입니다 — 통과한 변이표에서 구멍 둘이 나왔습니다.

## 정한 것과 다른 점

- spec 0004 **개정 5** — 상태 기록 주체를 명시하고, `AETHER_KNOWLEDGE_CHUNK_OVERLAP_CHARS` 를 표기에 맞추고, R-7 의 `smoke` 시나리오를 P3-3 뒤로 미루는 2.9.1 을 더했습니다.
