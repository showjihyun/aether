# P4-4 — HUMAN / APPROVAL (HITL) 🔒

Workflow 가 **사람을 기다립니다.** `START → AGENT → CONDITION → HUMAN → AGENT → END` 가 승인 대기에서 멈추고, 승인 API 를 부르면 재개되어 END 에 닿습니다 — Phase 4 를 정의하는 시나리오(R-4)가 여기서 성립합니다.

**이 단위는 병합 전에 사람이 봅니다**(H-1, DP-6). 에이전트는 PR 까지 가고 멈춥니다.

## 무엇이 생겼는가

- **승인 API 둘** — `POST /workflow-runs/{id}/approvals`(201)와 `GET /workflow-runs/{id}/approvals`. 거부 넷은 전부 정확성 가드입니다: `workflow_run_not_found`(404), `workflow_run_not_waiting_approval`·`node_execution_not_waiting`·`already_approved`(400).
- **마이그레이션 0008** — `waiting_node_execution_id` 열 둘(`control` 투영과 `data` 정본, FK 없음), 노드 실행 상태에 `waiting_approval`, 승인의 `unique(workflow_run_id, node_execution_id)`, 그리고 **`GRANT SELECT ON control.workflow_approvals TO aether_data`** 한 줄.
- **실행기의 `HUMAN`·`APPROVAL` 노드** — 같게 다루고 `waiting_approval` 로 파킹하며 **lease 를 놓습니다**. 재개는 `ApprovalReader` 가 읽은 **저장된 승인**으로만 합니다.
- **이벤트 둘** — `approval.requested`(파킹)·`approval.granted`(실행기가 승인을 관측). payload 에 **주체를 싣지 않습니다**.
- **스위퍼를 승인 대기까지** — `waiting_approval` 인데 승인이 이미 있는 건도 줍습니다(재큐가 유실돼도 멈추지 않습니다).
- **구조 테스트** — `tests/arch/test_approval_has_no_authorization_model.py`. 승인 경로에 권한 판정이 **없다는 것**을 AST 로 고정합니다.

## 왜 그렇게 했는가

- **권한 판정을 넣지 않았습니다**(spec 2.6·C-4). 인증된 주체 누구나 승인할 수 있고 "자기 승인 금지" 도 없습니다. v1 이 보장하는 것은 "승인 없이는 전진하지 않는다" 와 "누가 승인했는지 남는다" 둘이고, "누가 승인할 수 있는가" 는 Phase 8 입니다. 그럴듯한 반쪽 권한 모델은 이전 비용만 만듭니다. **그 공백을 테스트로 고정**해 둔 것이 이 단위의 특징입니다 — 나중에 누가 조용히 더하면 구조 테스트가 막습니다.
- **전진의 근거는 저장된 승인입니다.** 재큐 메시지를 근거로 삼으면 떠돌이 메시지 하나가 승인 없이 전진시킵니다(R-12 가 무너집니다). 그래서 실행기가 `control.workflow_approvals` 를 읽어야 했고, **SELECT 한 줄**을 더했습니다 — 0005 가 "필요해지면 검토를 거쳐 더한다" 고 비워 둔 자리입니다.
- **지목 대상을 `control` 에 투영했습니다.** R-12 의 `4xx` 는 api 가 내야 하는데 노드 실행은 `data` 에 있고 api 는 그 평면을 볼 수 없습니다. `waiting_run_id` 와 같은 모양으로 투영하고 상태에서 유도합니다. 투영에 값이 없으면 **어떤 노드 실행도 인정하지 않습니다**(fail-closed).
- **승인은 노드 실행당 한 건**입니다 — DB unique 가 동시 요청의 경쟁까지 막습니다. `already_approved` 를 상태 검사보다 **먼저** 보는 이유는, 실행기가 이미 전진한 뒤의 재전송도 "이미 승인됨" 으로 답해야 클라이언트가 성공을 구별하기 때문입니다.
- **`HUMAN` 과 `APPROVAL` 을 같게** 다룹니다 — 지금 다르게 만들면 쓰이지 않는 분기가 하나 남습니다.
- **이벤트에 주체를 싣지 않습니다.** 기록은 `control` 에 있고 조회로 봅니다 — 주체 id 를 스트림에 흘리지 않습니다.

## 정한 것과 다른 점

- **spec 2.2 의 노드 종류 목록에 `HUMAN`·`APPROVAL` 이 없었습니다** — 그런데 2.6 과 R-4 가 그것을 씁니다. spec 이 스스로 어긋나 있었고 **개정 6** 으로 열셋으로 고쳤습니다. 저장 때의 새 거부는 없습니다.
- **`GET /workflow-runs/{id}` 에 `waiting_node_execution_id` 를 노출했습니다** — 승인을 부르려면 클라이언트가 지목 대상을 알아야 합니다. 승인 **기록**을 넣은 것이 아니라 포인터입니다.
- **승인 리더가 Run 일관성을 JOIN 으로 한 번 더 봅니다**(브리프에 없던 추가) — API 를 거치지 않고 다른 Run 의 id 로 심어진 행이 엉뚱한 Run 을 전진시키지 못하게 하는 두 번째 방어선입니다.
- **`approval.requested` 가 `seq` 하나를 쓰는데 대응하는 상태 통지가 없습니다** — 투영에 빈틈이 생기지만 단조성은 유지됩니다.
- **red 순서가 일부 뒤바뀌었습니다** — 저장소 계약 둘, 승인 리더의 첫 테스트, 사슬 통합 셋은 구현 뒤에 썼습니다. 그 부분은 변이 여덟으로 갈음했습니다.
