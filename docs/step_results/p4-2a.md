# P4-2a — Workflow 실행기 · AGENT 노드 · 파킹과 재개

Workflow 가 **실행됩니다.** `START → AGENT → END` 를 api 로 시작하면 worker 가 집어 자식 Agent Run 을 띄우고, 그 동안 Workflow Run 은 **파킹**되어 worker 슬롯을 놓고, 자식이 끝나면 다시 집혀 END 까지 갑니다. 이 단위의 전부는 "대기가 자리를 쥐지 않는다"(R-7)·"재시작해도 이어 실행된다"(R-6)·"깨우는 신호가 두 번 와도 한 번만 전진한다"(R-8) 셋입니다.

PR 둘로 나눠 병합했습니다 — [#148](https://github.com/showjihyun/aether/pull/148)(골격, 대기 없음)과 [#149](https://github.com/showjihyun/aether/pull/149)(AGENT 노드와 파킹). 쪼갠 근거는 [plan 0005 부록 A](../../plans/0005-phase-4-workflow-engine.md) 에 있습니다.

## 무엇이 생겼는가

- **실행기** — `aether_workflow` 의 전진 유스케이스 하나(`advance_workflow_run.py`). 선언을 읽고 lease 를 잡고 노드를 전진시키고 `finally` 에서 놓습니다. 지원하는 종류는 `START`·`END`·`AGENT` 셋이고 나머지는 구별되는 사유로 `failed` 입니다.
- **마이그레이션 0006·0007** — `data.workflow_run_executions`(실행 상태·lease), `control.workflow_runs.requested_by`, 노드 실행 상태 enum(`data.workflow_node_execution_status`), 그리고 `control.runs` 를 가리키던 **FK 둘 제거**(아래).
- **Run 시작·조회 API** — `POST /workflows/{id}/runs`, `GET /workflow-runs/{id}`. 상태는 `control.workflow_runs` 의 **투영**이고 `aether:workflow_runs:status` 로 api 가 갱신합니다.
- **노드가 Agent 를 가리킵니다** — `agent_id`·`agent_version`(`LOOP` 의 `max_iterations` 와 같은 자리). 참조 없는 `AGENT` 는 저장 때 거부되고, 그래서 거부 사유가 **아홉 개**입니다.
- **자식 Agent Run 의 선언 경로** — 실행기가 id 를 정해 `aether:workflow:agent_runs:requested` 에 싣고 api 가 그 id 로 멱등 INSERT 뒤 `aether:runs:requested` 에 통지합니다.
- **재개 경로 둘** — `aether:runs:status` 의 Workflow 전용 consumer group(빠른 경로)과 **스위퍼**(`AETHER_WORKFLOW_SWEEP_INTERVAL_SECONDS`, 기본 30). 둘 다 하는 일은 재큐 하나입니다.
- **Workflow 자기 이벤트 어휘** — `workflow.status`·`node.started`·`node.finished`·`workflow.finished`(spec D-13). Agent Run 의 계약에 섞지 않았습니다.
- 문서 — [api.md](../api.md) 6·8·9절, [data-model.md](../data-model.md), [domain.md](../domain.md) 7절.

## 왜 그렇게 했는가

- **실행 상태를 `data` 에 뒀습니다.** 착수 전 GRANT 실측에서 worker 역할(`aether_data`)이 `control` 에 **SELECT 뿐**인 것을 확인했습니다(마이그레이션 0001·0005). GRANT 를 넓히면 평면 규칙(D-5)이 무너지고 권한 변경은 사람 검토 대상입니다. 그래서 `control` 쪽을 투영으로 고정했습니다 — Phase 1·3 이 이미 쓰는 모양입니다.
- **자식 Run 의 선언을 api 가 만듭니다.** worker 는 `control.runs` 에 INSERT 할 수 없습니다. id 를 **실행기가** 정하므로 같은 요청이 두 번 가도 선언은 한 행이고, 파킹은 처음부터 기다릴 대상을 압니다.
- **Version 해석을 실행기가 합니다.** api 가 풀게 하면 없는 Agent 를 가리킨 노드가 **영원히 파킹**됩니다(독약 메시지는 ack 되고 끝납니다). worker 는 `control.agent_versions` 에 SELECT 가 있으므로 직접 풀고, 없으면 노드를 실패시킵니다.
- **깨우는 신호를 상태 통지로 바꿨습니다.** spec 이 적은 `run.finished` 는 `aether:runs:{run_id}:events` 에 있고 그 스트림은 group 으로 받을 수 없습니다. 거기서 읽으려면 파킹 목록을 먼저 구해야 하고, 그러면 빠른 경로가 **스위퍼와 같은 장치**가 되어 "경로 둘" 이 하나로 붕괴합니다.
- **`waiting_run_id` 를 상태에서 유도합니다.** 투영은 `COALESCE(new, old)` 이고 스트림은 값 없는 선택 필드를 키 자체로 보내지 않아 "지워라" 를 표현할 수 없습니다. 그대로 두면 `succeeded` 인 Run 이 자식을 기다리는 것처럼 보입니다.
- **종결 한 쌍만 발행이 먼저입니다.** 종결 상태를 먼저 저장하면 그 창에서 죽었을 때 재전달이 "종결이면 아무것도 하지 않는다" 에 걸려 투영이 영영 `running` 으로 남습니다. 중복 가능성과 영구 불일치 중 전자를 택했습니다.
- **요청자를 자식에게 물려줍니다.** `requested_by` 를 비우면 기존 `GET /runs/{id}` 가 500 입니다. 사람 주체를 발명하지 않고 Workflow 를 시작한 주체를 그대로 넘깁니다 — 책임의 사슬이 끊기지 않습니다.
- **재전달이어도 자식이 아직 `queued` 면 다시 통지합니다.** 선언은 커밋됐는데 `XADD` 가 실패한 창이 있고, 그때 통지하지 않으면 자식이 `queued` 로 남아 그것을 기다리는 Workflow 가 영원히 파킹됩니다 — 스위퍼는 자식의 **종결**을 보므로 구하지 못합니다.

## 정한 것과 다른 점

- **plan 2절의 전제 하나가 틀렸습니다** — 실행 상태를 `control.workflow_runs` 에 쓴다는 것. worker 가 그 표에 쓸 수 없습니다(spec **개정 2**).
- **spec 이 적은 `run.finished` 를 쓰지 않았습니다** — 상태 통지 + Workflow 전용 group 입니다(**개정 3**).
- **노드 모델에 `agent_id`·`agent_version` 을 더했습니다** — 초안에는 그 자리가 없어 `AGENT` 노드가 무엇을 실행할지 말할 수 없었습니다(**개정 3**). 거부 사유가 여덟 → 아홉.
- **spec 개정 3 의 "`requested_by` 를 비웁니다" 를 구현이 고쳤습니다** — 비우면 자식 Run 의 조회가 500 입니다. 열을 더해 물려줍니다.
- **`control.runs` 를 가리키던 FK 둘을 제거했습니다**(마이그레이션 0007) — 자식 id 를 발사 **전에** 영속해야 하는데(R-8) 선언은 그 뒤에 생기므로 FK 가 거부하고, 파킹 통지와 선언이 다른 소비자로 도착해 경합하면 FK 위반이 투영 스레드를 죽입니다. **이것이 이 단위에서 사람 검토가 필요한 유일한 항목**이고 PR #149 에 그렇게 적었습니다.
- **PR 을 단위마다 하나가 아니라 둘로 냈습니다** — 근거는 plan 부록 A 입니다. 첫 PR 은 **대기를 전혀 만들지 않아** plan 1절의 금지선을 더 강하게 지킵니다.
- **노드 실행 기록에 `failure_reason` 을 더했습니다**(spec 에 없음) — 노드를 실패시킨 뒤 Workflow 를 종결하기 전에 죽으면 그 사유가 필요합니다.

## 남긴 것

- **자식 launch 의 `traceparent` 가 비어 있습니다.** 실행기에 tracer 포트가 없어 worker 의 trace 와 자식 Run 이 이어지지 않습니다 — Phase 1 의 `run.request` span 이 하는 일의 Workflow 판이 없습니다.
- **빠른 경로와 스위퍼의 경합 창 하나를 재현하지 못했습니다** — 자식이 파킹보다 **먼저** 끝나는 순간. 스위퍼가 덮지만 그 창을 직접 때리는 테스트는 없습니다.
- `WorkflowLeaseHeld` 로 ack 되지 않은 깨우는 메시지는 `XAUTOCLAIM` 의 65분 유휴까지 PEL 에 남습니다(Agent Run 과 같은 모양). 놓친 깨우기는 스위퍼가 덮습니다.
- 노드 출력과 `CONDITION` 은 **P4-2b** 입니다. 자식의 응답 본문을 읽는 코드를 만들지 않았습니다(D-8·C-3).
- `.importlinter` 에 "api 는 `aether_workflow.application`·`adapters` 를 import 하지 않는다" 계약 — **아직 없습니다.** 코드와 docstring 은 그 경계를 가정하지만 막는 것이 없습니다(보호 파일, 사람 결정).
