# P3-4 — Memory v1 (Knowledge 와 분리)

Agent 가 자기 경험을 남기고 다음 Run 에서 읽습니다. 핵심은 **섞지 않는 것**입니다 — 표도, 인덱스도, 쿼리도, 블록 표지도 Knowledge 와 따로입니다.

## 무엇이 생겼는가

- **`packages/memory` 가 빈 껍데기에서 벗어났습니다.** `MemoryEntry`·`MemoryHit`·`NewMemory`, inbound 포트 둘(`WriteAgentMemory`·`ReadAgentMemory`), outbound 포트 둘(`MemoryStore`·`Embedder`), 유스케이스 둘, 그리고 `data.agent_memory` 만 보는 `PostgresMemoryStore`.
- `AgentDefinition.memory_enabled`(기본 거짓). **새 HTTP 경로는 없습니다** — 기존 `PUT /agents/{id}` 가 새 Version 을 만듭니다(D-5).
- `aether_runtime` 의 `MemoryWriter` 포트. Executor 는 Run 이 `succeeded` 로 **종결된 뒤** 마지막 assistant 본문을 그대로 한 건 씁니다.
- `aether_context` 의 `MemoryReader` 포트와 `domain/memory.py` 의 `render_memory_block` — `[memory id=<id> created=<ISO8601> verified=false]…[/memory]`. Knowledge 블록과 **같은 문자열이 될 수 없습니다**.
- `CompileContextRequest.agent_id`·`memory_top_k`(기본 3), `ContextReport.source_tokens` 의 `memory`, 그리고 D-7 의 **맨 앞 자리**.
- worker `main` 의 조립 두 자리 — `MemoryReaderAdapter` 를 거친 읽기와 `WriteAgentMemoryUseCase` 를 꽂은 쓰기.
- **새 마이그레이션은 없습니다.** 표와 전용 HNSW 인덱스는 P3-2a 의 마이그레이션 0004 가 이미 만들어 뒀습니다.

## 왜 그렇게 했는가

- **spec 2.6 의 "Run 종결 시 남길 것이 있으면" 을 제가 좁혔습니다.** 트리거는 `memory_enabled` ∧ `succeeded`, 내용은 마지막 assistant 본문 **그대로 한 건**, 요약·분할·자동 승격 없음. 기준이 모호하면 구현마다 달라지고, 달라지는 것은 테스트할 수 없습니다. 이 구체화는 spec 개정으로 남깁니다.
- **종결 커밋 뒤에 씁니다.** 앞에서 쓰면 종결이 실패해 Run 이 재개될 때 같은 기억이 두 번 쌓입니다. 대가는 `run.finished` 이벤트가 몇 ms 먼저 나가는 것이고, 그쪽이 쌉니다.
- **쓰기 실패가 Run 을 실패시키지 않습니다.** Memory 는 부산물입니다. 예외를 삼키고 경고만 남기며, **경고에 본문을 넣지 않습니다** — 기억 본문에 무엇이 들어 있을지 모르니 로그에 흘리지 않습니다(AGENTS.md Trust).
- **`memory_enabled` 가 읽기도 막습니다.** 구현자가 지시에 없던 해석을 하고 보고했고, 받았습니다 — 끈 Agent 가 예전 기억을 계속 읽는다면 그 스위치는 거짓말입니다.
- **다른 임베딩 모델로 만든 기억은 조용히 제외합니다.** Knowledge 는 재적재를 요구하는 오류로 드러내지만(D-9), 기억에는 재적재할 원본이 없습니다 — 사람에게 요구할 것이 없는 실패를 오류로 올리지 않습니다.
- **`aether_context` 는 `aether_memory` 를 import 하지 않습니다.** 얇은 포트만 선언하고 worker 가 구조적으로 호환되는 유스케이스를 꽂습니다 — `.importlinter` 에 새 계약을 더하지 않고, P3-3 의 `KnowledgeSearch` 와 같은 자리입니다.
- **임베딩 어댑터는 하나입니다.** 리뷰에서 Knowledge 용과 Memory 용 `ModelGatewayEmbedder` 가 각자 gateway(= 각자 httpx 연결 풀)를 만들고 있어 하나로 합쳤습니다. "같은 임베딩 모델을 쓴다" 는 사실이 주석이 아니라 코드에 있는 편이 낫습니다.

## 정한 것과 다른 점

- **`ContextCompiler` 포트 시그니처에 `agent_id` 를 더했습니다.** 제 브리프에 없었지만 Executor 가 Compiler 에 Agent 를 알릴 길이 달리 없습니다. 기본값 `None` 이라 기존 호출자는 그대로입니다.
- **`RunDeclaration.agent_id` 가 생겼습니다.** `control.runs` 는 `agent_version_id` 만 들고 있어 reader 가 `control.agent_versions` 를 조인합니다.
- **`memory_enabled` 를 `Field(default_factory=bool)` 로 선언했습니다.** 평범한 `= False` 는 OpenAPI 에 `default` 를 싣고, 생성된 sdk 타입이 이 필드를 **필수**로 만들어 이 필드를 모르는 기존 클라이언트 요청이 타입 오류가 됩니다. `tools`·`knowledge` 와 같은 모양입니다 — 이 저장소의 `AgentDefinition` 스키마에는 `default` 를 싣는 필드가 하나도 없습니다.
- **`memory_top_k` 는 `AgentDefinition` 에 노출하지 않았습니다.** 요청 기본값 3 을 씁니다. Agent 별 조절은 필드가 필요해질 때 더합니다.
- **기본값 거짓 테스트의 red 를 못 봤습니다.** 뼈대에 필드가 먼저 있었습니다 — 기본값을 `True` 로 바꿔 실패를 확인한 변이 증거로 받았습니다.
- **`timed_out` 경로에는 별도 테스트가 없습니다.** 취소·실패와 같은 `_finalize` 를 지나고 성공 분기에서만 기록을 부르는 구조이며, 그 구조는 취소·실패 테스트가 고정합니다.
