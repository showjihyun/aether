# P3-2a — pgvector 교체 · 마이그레이션 0004 · 임베딩 모델 분리 (PR #117)

Phase 3 의 첫 단위. plan 0004 가 이것을 먼저 둔 이유는 **가장 깨질 가능성이 큰 것**이기 때문입니다 — 데이터베이스 이미지를 바꾸는 일입니다.

## 무엇이 생겼는가

- compose 의 PostgreSQL 이미지가 `pgvector/pgvector:pg16`(다이제스트 핀)으로 바뀌었습니다. 다이제스트는 실제 조회로 확인했고(index 다이제스트 — 기존 핀과 같은 종류인 것까지 `imagetools` 로 맞췄습니다) 추측하지 않았습니다.
- 마이그레이션 **0004**: `vector` 확장, spec 2.8 의 네 표(`control.knowledge_sets`·`control.knowledge_ingestions`·`data.knowledge_chunks`·`data.agent_memory`), HNSW 코사인 인덱스 **둘**(Knowledge 와 Memory 가 별도 표·별도 인덱스 — R-10 의 전제), GRANT 는 Phase 2 의 방향 그대로. 벡터 차원은 `AETHER_EMBED_DIM`(기본 768).
- 임베딩 모델이 채팅 모델과 **분리**되었습니다(`AETHER_EMBED_MODEL_ID`, 기본 `nomic-embed-text`).
- `docs/data-model.md` 가 네 표와 이미지 교체를 반영했습니다. 그 문서가 스키마·역할·GRANT 의 정본입니다.

## 왜 그렇게 했는가

- **새 서비스를 늘리지 않았습니다**(D-1). 전용 Vector DB 를 넣으면 백업·권한·마이그레이션 경로가 하나 더 생깁니다. pgvector 는 그 세 가지를 이미 있는 것에 얹습니다.
- **차원을 마이그레이션 시점에 고정**했습니다. 임베딩 모델을 바꿔 차원이 달라지면 **새 마이그레이션**이 필요합니다 — 자동 변환을 넣지 않은 것은 기존 벡터와 새 차원이 조용히 섞이는 것을 막기 위해서입니다(C-3·D-9).
- **임베딩 모델을 분리한 것은 선택이 아니라 수정입니다**(D-3). 그 전까지 어댑터는 채팅 모델 id 를 `/embeddings` 로 보냈습니다. 그대로 두면 적재가 **반드시** 실패합니다. 적재 경로가 없던 동안에는 아무도 그 코드를 부르지 않아 드러나지 않았습니다.
- `alpine` → Debian 전환이 init 스크립트에 닿는지가 이 단위의 실제 위험이었습니다. 전용 회귀 테스트가 **실제 이미지로** `01-roles.sh` 를 다시 확인합니다.

## 정한 것과 다른 점

- plan 의 P3-2a 문구를 실제 구조에 맞췄습니다(plan 개정 1) — `compose.smoke`·`ci`·`offline` 은 PostgreSQL 이미지를 지정하지 않습니다. 실행자가 찾은 불일치입니다.

## 남긴 것

- 이미지 크기가 **111 MiB → 152 MiB**(+37%) 입니다. 이 숫자는 P3-5 의 기록 대상입니다.
- 한계 하나를 그대로 받았습니다 — `control` 역할의 `data` 접근 거부 테스트는 표가 없어도 통과합니다(스키마 단계 거부가 먼저 걸립니다). 기존 패턴과 같은 성질이고, 그 사실을 보고에 적었습니다.
