# P5-3 — Workflow Run 상세의 노드 목록

노드 단위가 **화면에 보입니다.** 투영(P5-1) → 조회(P5-2) → 화면의 사슬이 여기서 **읽기로 한 번 끝났습니다** — 쓰기 경로를 열기 전입니다(P5-4). 이 단위의 전부는 spec 0007 **R-6**("노드별 상태·시작·종료가 보이고 실패한 노드를 가리킨다") 하나입니다.

## 무엇이 생겼는가

- **`/workflows/runs/{id}`** — `apps/web/app/workflows/runs/[id]/page.tsx`·`loading.tsx`·`page.test.tsx`. 서버 컴포넌트가 `createClient` 로 `listWorkflowRunNodes(id, { cursor })` 를 직접 부릅니다(`/runs/[id]` 와 같은 길).
- **열 여섯** — 노드, 종류, 상태 `badge`, 시작, 종료, 실패 사유. `LoadMore` 로 커서를 잇습니다.
- **실패한 노드의 구별** — 행에 `data-failed="true"`·배경(`bg-destructive/10`)·굵은 이름, 실패 사유는 mono, 그리고 표 위에 `role="status"` 로 **"실패한 노드 N개"**. 실패가 없으면 그 문장도 없습니다.
- **상태 넷이 서로 다른 화면** — 404(「Workflow 실행을 찾을 수 없습니다」 + 목록 링크), 그 밖의 오류(새로고침 안내), 깨진 커서 422(「처음부터 보기」), 빈 목록(표 없이 한 줄). 키가 없으면 **부르지 않고** `MissingApiKey`, 로딩은 6열 skeleton.
- **목록에서 가는 길** — `app/workflows/page.tsx` 실행 표의 상태 칸에 「노드 보기」 링크. 같은 파일의 주석 **"노드 실행 목록은 없습니다 — 그 API 가 없습니다"** 를 지웠습니다. 이제 있습니다.
- 문서 — `DESIGN.md` 5절(새 화면 행 + `/workflows` 행의 "노드 단위는 보여주지 않습니다" 철회), `plans/0007` **개정 1**(아래).

## 왜 그렇게 했는가

- **중계(`lib/relay.ts`)를 넓히지 않았습니다.** plan 의 P5-3 「주의」는 `ALLOWED_ROUTES` 에 `GET workflow-runs/:id/nodes` 를 더한다고 적었지만, 실측하면 목록·상세 화면은 **서버에서 서버로** 부르고 중계는 브라우저가 부르는 경로(이벤트 스트림)에만 쓰입니다. 그대로 따르면 **쓰이지 않는 공개 표면**이 늘고, `route.test.ts` 가 `ALLOWED_ROUTES.length` 를 넷으로 고정한 **의도된 지뢰선**을 이유 없이 지웁니다. 중계는 키를 들고 있어 열어 둔 만큼이 그대로 공개됩니다(그 파일 주석). plan 쪽을 고쳤습니다(개정 1).
- **`card` 머리를 두지 않았습니다.** Run 수준의 상태·요청 시각을 보여주려면 SDK 에 `getWorkflowRun` 이 필요하고 그것은 이 단위 밖입니다. 비는 카드는 `DESIGN.md` 9절이 금지하는 자리표시이고, `/runs/{id}` 가 "입력" 탭을 두지 않은 것과 같은 판단입니다.
- **실패를 색으로만 구별하지 않았습니다.** 배경 외에 굵은 이름·실패 사유 텍스트·요약 문장이 함께 있습니다 — `DESIGN.md` 8절이고, P5-8 의 a11y 러너가 숫자로 보기 전에 지킬 수 있는 선입니다.
- **노드 출력 열이 없습니다**(spec 0007 D-4). 조회 응답에 아예 없고, 자리표시도 두지 않습니다 — spec 0005 D-8 의 문을 열지 않습니다. 그 사실을 보는 테스트가 따로 있습니다.
- **상태 `badge` 는 기존 `WorkflowRunStatusBadge` 를 그대로 씁니다.** 노드 상태 여섯 값이 `WorkflowRunStatus` 의 부분집합이라 타입으로 묶입니다 — 두 번째 badge 컴포넌트를 만들면 같은 표현이 두 곳에서 갈라집니다.
- **새 열을 만들지 않고 링크를 상태 칸에 뒀습니다.** 기존 `page.test.tsx` 가 실행 표의 열 머리글을 고정하고 있고, 열을 늘리는 것은 이 단위가 요구받은 것이 아닙니다.

## 정한 것과 다른 점

- **중계 변경 0건** — plan 초안이 적은 "유일한 중계 변경" 을 하지 않았습니다. `plans/0007` **개정 1** 이 그 줄을 고쳤습니다.
- **Run 머리 카드 없음** — plan 은 "노드별 상태·시각·실패 사유를 행으로" 만 요구했고 머리 카드를 적지 않았습니다. 없는 것을 그리지 않았습니다.
- 그 둘 말고는 plan 0007 2절의 P5-3 표와 같습니다.

## 남긴 것

- **자동 갱신이 없습니다.** 돌고 있는 Workflow Run 의 노드 상태는 새로고침해야 바뀝니다. 브라우저 쪽 재조회를 넣으려면 중계를 넓히는 결정이 먼저이고(위), 그 판단은 캔버스가 읽을 것이 생기는 **P5-5·P5-6** 에서 함께 합니다.
- **Run 수준 머리 카드**는 SDK 에 `getWorkflowRun` 이 생기면 그때입니다. 지금 그 함수를 더하는 것은 이 단위 밖입니다.
- **회차(`iteration`)와 노드 출력**은 여전히 보이지 않습니다 — 투영이 노드당 한 행이고(P5-1), 출력은 `data` 에 머뭅니다(D-4).
- **`e2e` 판정**(실행한 Workflow Run 의 노드 이름이 행으로 보인다)은 **P5-9** 입니다.
- **그래프 그림은 없습니다** — P5-5 이고 캔버스 의존은 **H-1**(사람)이 1절에서 정합니다.
