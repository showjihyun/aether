# P4-3 — PARALLEL / JOIN / LOOP / WAIT

Workflow 가 **갈라지고, 합치고, 돌고, 기다립니다.** 노드 종류가 다 찼고(LLM·MCP·TOOL 만 남음) 그 과정에서 실행기의 전진 모델이 한 번 바뀌었습니다.

## 무엇이 생겼는가

- **전진 모델이 기록 기반이 됐습니다** — 전진할 수 있는 노드는 "들어오는 간선이 모두 결판나고 그중 하나 이상이 활성" 인 노드이고 근거는 `data.workflow_node_executions` 입니다(`domain/progress.py`). `current_node_id` 는 **관측용**("마지막으로 전진한 노드")으로 뜻이 좁아졌습니다.
- **`PARALLEL` → `JOIN`** — 분기를 차례로 전진시키고 합류에서 기다립니다. `JOIN` 의 출력은 분기별 결과이고 상한을 넘기면 **가장 큰 분기 출력부터** `null` 로 바꿉니다. 분기 하나라도 실패하면 `failed` + `branch_failed`.
- **`LOOP`** — `CONDITION` 과 **같은 판정식 키**를 쓰고 `true` 가 본문, `false` 가 탈출입니다. 회차는 `iteration` 이고 상한을 넘기면 `failed` + `loop_limit_exceeded`. 저장 때 거부는 `CONDITION` 의 **두 사유를 재사용**합니다.
- **`WAIT`** — `waiting_timer` + `wake_at` 으로 **파킹**합니다. 새 상태와 열(마이그레이션 0009), `wait_seconds`(필수, 없으면 `wait_node_without_duration` — 사유 **열두 개**), 그리고 **스위퍼의 셋째 가지**.
- **파킹 순서 수정** — 상태 저장 → `release` → 이벤트·통지. 세 파킹 경로 전부.

## 왜 그렇게 했는가

- **"현재 노드" 하나로는 분기를 말할 수 없습니다.** 기록이 이미 진행을 알고 있으므로(`unique(run, node, iteration)`) 거기서 읽는 것이 상태를 하나 더 만드는 것보다 쌉니다. 타지 않은 분기의 하류가 실행되지 않는 것도 같은 근거에서 나옵니다.
- **`PARALLEL` 의 동시성을 보장하지 않습니다**(개정 7). 자식 Run 을 가진 분기를 진짜 동시에 돌리려면 "여럿을 기다리는" 모델이 필요하고 `waiting_run_id` 는 하나입니다. Phase 4 의 목표는 표현력이지 처리량이 아닙니다(C-5) — **보장하지 않는 것을 보장하는 척하지 않는 쪽**을 골랐습니다.
- **`LOOP` 이 본문 출력으로 끝날 수 있어야 합니다**(개정 8). `CONDITION` 의 규칙을 그대로 쓰면 첫 판정에서 경로가 없어 실패하고, 조건 루프가 **상한 초과로만** 끝납니다. 그래프에 **있는** 노드의 이번 회차 기록이 없을 때만 "계속" 으로 읽고, 오타는 그대로 시끄럽게 실패합니다 — 조용한 거짓을 만들지 않는다는 P4-2b 의 규칙을 깨지 않습니다.
- **`WAIT` 는 파킹입니다.** 실제 시간을 블록하면 그것이 D-4 가 금지한 슬롯 점유이고, 한 시간짜리 `WAIT` 가 worker 하나를 한 시간 먹습니다.
- **파킹이 lease 를 발행보다 먼저 놓습니다**(개정 8). "상태는 대기인데 lease 는 잡힌" 창이 실제로 관측됐습니다 — 전량 통합 3회 중 2회에서 승인 파킹의 lease 단언이 흔들렸습니다. 테스트를 느슨하게 하는 대신 **불변식이 항상 참이도록** 순서를 고쳤습니다. SQL 로 들여다보는 사람이 R-7 이 깨졌다고 읽으면 안 됩니다.

## 정한 것과 다른 점

- **`PARALLEL` 이 동시 실행이 아닙니다** — spec 2.7 의 "분기를 모두 실행" 은 지키고 "병렬" 의 뜻을 **순차**로 고정했습니다(개정 7).
- **`JOIN` 출력의 자르기 규칙을 구현이 정했습니다** — spec 에 "분기 출력의 합이 넘칠 때" 가 없어서 가장 큰 것부터 `null` 로 바꾸는 쪽으로 정했습니다.
- **나가는 간선이 하나뿐인 `PARALLEL`** 은 새 거부를 만들지 않고 한 분기로 실행합니다.
- **어느 `END` 든 먼저 마치면 Run 이 `succeeded`** 입니다 — 끝나지 않은 다른 분기를 기다리지 않습니다.
- **`LOOP` 중첩과 do-while 모양은 v1 범위 밖**입니다(`progress.py` docstring).
- **`release` 가 두 번 불립니다**(파킹 경로 + `finally`) — 같은 owner 조건부 UPDATE 라 무해하고, 그 때문에 호출 목록을 보던 단위 테스트 둘을 집합 비교로 바꿨습니다.
- **`wake_at` 을 `GET /workflow-runs/{id}` 에 노출했습니다** — `waiting_run_id` 와 같은 투영 규칙입니다.
- **red 순서가 일부 뒤바뀌었습니다** — `WAIT` 통합 테스트와 첫 물결의 일부는 구현 뒤에 썼고 변이로 갈음했습니다.

## 남긴 것

- **파킹이 있는 `PARALLEL`·`LOOP` 를 실제 DB 로 돌지 않았습니다** — 통합은 파킹 없는 노드로만 돌렸고, 파킹·재개는 fake 단위 테스트가 증명합니다.
- **이벤트 하나가 사라질 수 있습니다** — 파킹이 lease 를 먼저 놓으므로, 그 틈에 다른 worker 가 더 큰 `seq` 를 먼저 발행하면 뒤늦은 파킹 이벤트가 explicit ID 규칙에 걸려 버려집니다. 순서가 섞이지는 않고 상태·투영은 멱등입니다.
- **긴 루프에서 읽기 횟수가 늡니다** — 전진할 때마다 노드 실행 기록을 읽고 판정식이 있는 노드는 한 번 더 읽습니다.
- **`wait_seconds` 에 상한이 없습니다.**
- `fakes.replace_output` 이 쓰이지 않게 됐습니다(지우지 않았습니다).
