# P4-1 — Workflow 모델과 영속 (마이그레이션 0005)

Workflow 를 **저장**할 수 있게 됐습니다. 실행은 아직 없습니다. 이 단위의 전부는 "잘못된 그래프가 저장되지 않는다" 와 "저장된 Version 은 바뀌지 않는다" 둘입니다.

## 무엇이 생겼는가

- **`packages/workflow` 가 빈 껍데기에서 벗어났습니다.** `domain/` 에 `NodeKind`(11종), `Node`·`Edge`·`WorkflowVersion`(전부 frozen), `WorkflowRunStatus`(7값)와 전이표, 결정적 직렬화(`serialize_version`), 그리고 **검증 순수 함수**(`validate_version`)와 사유 enum `Reason`(8값).
- **마이그레이션 0005** — spec 2.9 의 **다섯 표 전부**와 GRANT. `control.workflows`·`workflow_versions`·`workflow_runs`·`workflow_approvals`, `data.workflow_node_executions`. 상태는 새 enum `control.workflow_run_status` 이고 `data.run_execution_status`(0001)는 건드리지 않았습니다.
- **불변성을 DB 가 지킵니다** — `workflow_versions_immutable`·`workflow_approvals_immutable` 트리거(`agent_versions_immutable` 과 같은 모양).
- **정의 API 네 경로** — `POST /workflows`, `GET /workflows/{id}`, `PUT /workflows/{id}`(새 Version), `GET /workflows/{id}/versions/{n}`. `apps/api` 에 도메인·inbound 포트·유스케이스·PostgreSQL 저장소·라우터.
- `apps/api` 가 **`aether_workflow.domain` 만** 의존합니다(`node`·`workflow_version`·`validation` 세 모듈). `pyproject.toml` 에 workspace 의존성 한 줄.
- `packages/sdk/openapi.json` 과 생성 타입 — **추가만**(새 경로 3개·메서드 4개·스키마 9개, 기존 경로·스키마 변경 0건).
- 문서 — [domain.md](../domain.md) 7절(용어), [api.md](../api.md) 8절(계약), [data-model.md](../data-model.md) 2절의 두 묶음과 3절의 트리거 두 줄.

## 왜 그렇게 했는가

- **검증은 `domain` 의 순수 함수입니다.** I/O 가 없으니(AR-9) DB 없이 판정되고, 같은 함수가 저장 경로와 실행 경로에서 같은 답을 냅니다. 라우터는 예외를 상태 코드로 옮기는 일만 합니다.
- **거부는 `400` 이고 `422` 를 쓰지 않았습니다.** FastAPI 의 요청 모양 검증이 `422` 를 이미 쓰므로, 겹치면 클라이언트가 "그래프가 틀렸다" 와 "JSON 이 틀렸다" 를 구별할 수 없습니다. 대신 본문에 `violations[]` 를 더해 사유를 **전부** 돌려줍니다 — 한 번에 하나씩 고치게 만들지 않습니다.
- **다섯 표를 한 마이그레이션에 넣었습니다.** `workflow_approvals` 를 쓰는 단위는 P4-4 이고 `workflow_node_executions` 는 P4-2a 입니다. 그래도 표를 지금 만든 이유는 **평면·역할·GRANT 검토가 한 번의 위험 표면**이기 때문입니다 — 마이그레이션 0003 이 P2-4 의 `control.tool_permissions` 를 함께 만든 것과 같은 선택입니다.
- **`aether_data` 에 SELECT 만 줬습니다.** worker 는 실행할 그래프(`workflow_versions`)와 Run 선언(`workflow_runs`)을 읽습니다. `workflows`(이름)와 `workflow_approvals`(승인 기록)에는 **아무 권한도 주지 않았습니다** — 지금 필요가 없고, 필요해지는 단위에서 사람 검토를 거쳐 더하는 쪽이 낫습니다.
- **`workflow_approvals.node_execution_id` 에 FK 를 두지 않았습니다.** `control` → `data` 참조는 평면 경계를 거스릅니다. "지목한 실행이 정말 대기 중인가" 는 FK 가 답할 수 있는 질문이 아니고, P4-4 의 애플리케이션 판정입니다(R-12).
- **자식 Run 연결은 workflow 쪽에 뒀습니다.** `data.workflow_node_executions.agent_run_id` 입니다. Run 쪽에 Workflow 참조를 두면 `aether_runtime` 이 workflow 를 알아야 하고 그것이 **AR-13 위반**입니다(D-1·D-3).
- **`unique(run, node, iteration)` 을 걸었습니다.** 멱등 재개(R-8)는 P4-2a 의 일이지만, 마지막 방어선을 DB 에 두면 애플리케이션 버그가 중복 전진으로 번지지 않습니다.
- **`node_executions.status` 는 text 입니다.** 노드 실행 상태의 집합이 spec 에 없습니다. 없는 집합을 미리 enum 으로 굳히면 P4-2a 가 마이그레이션을 하나 더 쓰게 됩니다 — 실행기가 집합을 정한 뒤 좁힙니다.

## 정한 것과 다른 점

- **spec 2.2 의 여섯 거부가 사유 여덟이 됐습니다**(spec 0005 **개정 1**). START 거부를 `no_start`·`multiple_start` 로 나눴고(R-1 이 "0개·2개 각각" 을 요구합니다), **`duplicate_node_id` 를 새로 더했습니다** — 같은 id 를 가진 노드 둘이 검증을 통과하는 구멍을 리뷰에서 찾았습니다(실측: 위반 0건으로 통과, 저장에서 PK 충돌로 500). 저장 때 4xx 로 잡는 쪽이 낫고 근거는 `dangling_edge` 와 같습니다.
- **`PARALLEL` ~ `JOIN` 의 "대응" 을 v1 에서 정의했습니다**(개정 1). 하류에 `JOIN` 이 하나라도 있으면 통과이고, 중첩 `PARALLEL` 의 짝 맞추기와 `JOIN` 이 모든 분기를 받는지는 **검사하지 않습니다**. spec 초안이 "대응" 을 정의하지 않아 구현이 해석해야 했고, 그 해석을 문서에 올리지 않으면 P4-3 에서 조용히 갈라집니다.
- **`aether_workflow` 에 두었던 정의 inbound 포트를 지웠습니다.** 제 브리프가 그것을 만들라고 했는데 틀렸습니다 — 정의 경로는 Control Plane 의 것이고 api 는 `aether_workflow.application` 을 import 하지 않으므로(AR-7 과 같은 경계) 쓰이지 않는 사본이 한 벌 생겼을 뿐입니다. 포트는 `aether_api` 에만 둡니다. 실행 쪽 inbound 포트는 P4-2a 에서 `aether_workflow` 에 생깁니다 — 그것은 worker 가 씁니다.
- **spec 이 열어 둔 열을 구현이 채웠습니다.** `workflow_runs` 의 `input`·`status_seq`·`current_node_id`·`waiting_run_id`·`cancel_requested_at`, `node_executions` 의 `iteration`·`status`·`output`·`output_truncated`·`failure_reason`. spec 2.9 는 표의 목적만 정했고 열 목록은 정하지 않았습니다.
- **`workflows.name` 에 unique 제약을 두지 않았습니다.** `control.agents` 와 다릅니다 — spec 에 그 요구가 없습니다. 필요해지면 다음 마이그레이션입니다.
- **빈 통합 단언 하나를 변이로 대신했습니다.** "`aether_control` 이 `data` 에 접근 못 함" 은 스키마 USAGE 단계에서 거부되어 마이그레이션이 없어도 통과합니다(vacuous). 그래서 GRANT 를 일부러 넓히는 변이로 그 단언이 실제로 발화하는 것을 확인했습니다.

## 남긴 것

- **`aether_data` 는 `workflow_runs` 에 SELECT 만 있습니다.** worker 가 상태·lease 를 쓸 자리가 없습니다. 이것은 결함이 아니라 spec D-5 와 Phase 1 의 모양입니다 — Agent Run 도 worker 가 스트림으로 상태를 보내고 api 가 투영합니다. **P4-2a 가 이 자리에서 GRANT 를 넓히는 쪽으로 가지 않도록** 적어 둡니다: 필요한 것은 `data` 쪽 실행 상태이고, 그 표를 더하는 것이 평면 규칙을 지키는 길입니다.
- `node_executions.status` 의 값 집합(→ P4-2a 가 정하고 enum 으로 좁힘).
- `.importlinter` 에 "api 는 `aether_workflow.application`·`adapters` 를 import 하지 않는다" 계약을 더할지 — **지금은 더하지 않았습니다.** 실측으로 api 의 import 가 `domain` 세 모듈에 머물렀고(위), 계약은 위반이 가능해진 뒤에 세우는 것이 아니라 **지킬 이유가 생겼을 때** 세웁니다. P4-2a 가 api 에서 실행 쪽을 보려는 유혹이 생기는 단위이므로 그때 다시 판단합니다.
- `aether-api openapi` 의 cp949 실패 — 제품 CLI 가 파일을 로케일 인코딩으로 씁니다. 이 단위에서 고치지 않았습니다(범위 밖).
