# P5-9 — `e2e` 가 만드는 경로를 지납니다 (브라우저 없이)

**이제 `e2e` 의 실행 하나가 `apps/web` 의 서버 액션을 실제로 지나 Workflow 를 만들고, 그 이름이 `/workflows` 목록에 행으로 보입니다.** 이 단위의 어려움은 쓰기가 아니라 **세 문서가 동시에 성립하지 않는 것처럼 보였던 것**이었습니다.

## 무엇이 생겼는가

- **확인 하나** — `scripts/web_write_check.py`. 표준 라이브러리만 쓰고 **api 컨테이너 안의 python** 이 실행합니다(spec 0006 D-20). 순수 함수는 `chunk_paths`·`find_action_id`·`parse_action_result`·`check_listed`·`build_graph_args` 입니다.
  1. `GET http://web:3000/workflows/new` → HTML 에서 `/_next/static/chunks/*.js` 를 모읍니다.
  2. 그 청크에서 `createServerReference)("<hex>", …, "createWorkflowAction")` 꼴을 찾아 **액션 id 를 이름으로** 얻습니다(해시를 코드에 적지 않습니다 — 빌드마다 바뀝니다).
  3. `POST /workflows/new` 에 `Next-Action: <id>` 와 본문 `["<이름>","<START→END 그래프 JSON 문자열>"]`.
  4. 응답의 `ok:true` 를 보고, `/workflows` HTML 에 그 이름이 있는지 봅니다.
- **`scripts/e2e.sh`** — R-5 확인 **뒤에** 그 호출 구간. 이름은 실행마다 다릅니다(`e2e-ui-$$-${RANDOM}`), 그래서 R-5 가 쓰는 이름과 겹치지 않습니다.
- **테스트** — `tests/scripts/test_web_write_check.py`(8건), `tests/scripts/test_e2e_script.py`(+4건), `tests/scripts/_fake_docker.py` 에 `web-write-check` 분기와 `FAKE_WEB_WRITE_OUT`·`FAKE_WEB_WRITE_EXIT`.

**제품 코드는 한 줄도 바뀌지 않았습니다** — 폼·서버 액션·SDK·화면·`lib/relay.ts` 의 `ALLOWED_ROUTES`(**넷** 그대로) 전부입니다.

## 왜 그렇게 했는가

- **세 문서가 모두 성립합니다.** spec 0007 **R-8** 은 "화면을 통해(서버 액션 경로)", spec 0006 **D-20** 은 "브라우저를 띄우지 않습니다", `DESIGN.md` **7.2** 는 "인자는 원시 타입만, `FormData` 를 통째로 받지 않습니다" 입니다. 실측하면 쓰기 폼 **넷 전부가 `onSubmit`**(JS)이라 HTML 만으로 액션을 부를 길이 없고, `<form action={서버액션}>` 으로 바꾸면 인자가 `FormData` 로 와서 **7.2 를 어깁니다**. 그래서 폼을 고치는 대신 **브라우저의 React 클라이언트가 하는 것과 같은 HTTP 호출**을 python 이 직접 합니다 — 셋 중 어느 것도 고치지 않고 셋을 다 지키는 길입니다.
- **액션 id 를 이름으로 찾습니다.** 해시는 빌드마다 바뀌므로 적어 두면 다음 빌드에서 거짓으로 깨지거나(또는 더 나쁘게) 엉뚱한 액션을 부릅니다. Next 가 `createServerReference` 의 마지막 인자로 **함수 이름을 보존**하므로 그것을 지표로 씁니다.
- **빌드 산출물을 뒤지지 않습니다.** 보는 것은 web 이 **공개한 응답**(HTML 과 그것이 참조하는 청크)뿐입니다 — `web_routes_check.py` 가 하던 일과 같은 종류입니다.
- **종류별 칸이 없어도 저장되는 그래프**(`START → END`)를 씁니다. `AGENT`·`LLM` 류는 지금 400 으로 거절되는 것이 계약입니다(`p5-6.md` 의 「남긴 것」).
- **쓰기를 R-5 뒤에 둡니다.** 읽기 여섯 경로 확인이 먼저 성립해야 쓰기 실패의 원인이 "화면이 안 떴다" 와 구별됩니다.

## 하네스 근거

- **red 증거 ①**(구현 전) — `tests/scripts/test_e2e_script.py` 의 새 2건이 `assert 0 != 0` 으로 실패했습니다. **지금의 `e2e` 는 쓰기 경로를 지나지 않고도 0 으로 끝난다**는 것이 그 실패의 내용입니다. `test_web_write_check.py` 는 `ModuleNotFoundError: No module named 'scripts.web_write_check'` 로 수집 단계에서 실패했습니다.
- **돌연변이 증거 ①**(거짓 성공 경로 그 자체) — `ACTION_NAME` 을 `"noSuchAction"` 으로 바꾸고 못 찾았을 때를 `return 0` 으로 바꾸자 **실제 스택 `e2e` 가 통과**했습니다(rc=0). 로그에는 `web_write_check: ok` 줄 **없이** `[R-8/0007] ok` 와 `e2e: pass` 가 찍혔습니다 — 쓰기 경로를 지나지 않고 초록입니다.
- **그 구멍을 리뷰에서 반려했고 닫았습니다.** `scripts/e2e.sh` 가 종료 코드만 보고 있었습니다. 이제 확인의 출력을 받아 **성공 표식 `web_write_check: ok` 를 먼저 확인**하고(없으면 `fail`), 그다음 종료 코드를 봅니다. 출력은 로그에 그대로 다시 내보냅니다. 선례는 같은 파일의 R-10 구간이 종료 코드와 함께 `grep -Eq '"status": ?"succeeded"'` 로 **내용**을 보는 것입니다.
- **돌연변이 증거 ②**(고친 뒤) — 같은 돌연변이로 `verify.sh --only e2e` 가 **rc=1**, 로그에 `e2e: FAIL R-8 (spec 0007): web_write_check exited 0 without its success marker - the write path was not proven`. 원복 후 rc=0 이고 `web_write_check: ok - Workflow created through the server action and listed` 가 찍힙니다. 원복은 `grep` 과 `git status`(변경 파일 5개)로 확인했습니다.
- **셸의 구조를 테스트가 고정합니다** — 출력이 비면 e2e 가 실패한다는 것, 성공 표식이 로그에 남는다는 것, 쓰기 확인이 읽기 확인 **뒤**에 오고 이름이 실행마다 다르다는 것.
- `tests/scripts` **205 passed**, ruff·mypy 통과. 로컬 전량은 아래.
- **`e2e` 는 로컬 기본 실행에서 미뤄집니다**(`HARNESS_DEFERRED_STEPS`, 사람 결정 2026-10-11). 그래서 이 단위의 판정은 `--only e2e` 실행과 **CI 의 `--full`** 이 소유합니다 — CI 에서 `required=true` 그대로입니다.

## 정한 것과 다른 점

- **plan 의 「만드는 것」은 "Agent 또는 Workflow 중 적어도 하나" 입니다** — Workflow 한 고리로 충족했고 Agent 생성·수정은 더하지 않았습니다. 늘리면 `e2e` 가 길어지고, R-8 이 요구하는 것은 **쓰기 경로가 실제 스택에서 한 번 지나는 것**입니다.
- **`tests/scripts/` 도 고쳤습니다**(과제 문구는 `scripts/` 만 적었습니다). 가짜 docker 에 분기가 없으면 새 호출이 **조용히 0 을 반환**해 테스트가 공허해지기 때문입니다. 보호 파일은 아닙니다.
- **읽기 확인에 함수를 더하지 않고 새 파일로 나눴습니다** — `test_web_routes_check.py` 가 `ROUTES` 와 `_EXPECT_ENV` 의 드리프트를 보는데 쓰기 확인을 섞으면 그 검사가 흐려집니다.

## 남긴 것

- **`e2e` 가 Next 의 액션 호출 형식에 결합되었습니다.** 의존하는 것 셋 — HTML 이 `/_next/static/chunks/*.js` 를 참조한다는 것, 청크에 `createServerReference)(…, "<액션 이름>")` 꼴이 있다는 것, 그 호출이 `Next-Action` 헤더 + JSON 배열 본문을 받는다는 것. **깨지면 조용히 넘어가지 않습니다** — 청크가 없으면 `no /_next/static/chunks/*.js referenced`, 이름이 없으면 `server action 'createWorkflowAction' not found in N chunk(s) - the write path was not exercised` 로 e2e 가 실패합니다. 액션 함수 이름을 바꾸거나 Next 를 올려 번들 모양이 바뀌면 `ACTION_NAME` 과 정규식을 함께 고쳐야 합니다.
- **화면의 폼 자체는 여전히 실제 스택에서 판정되지 않습니다**(C-1 의 비대칭이 완전히 사라진 것은 아닙니다). 지나는 것은 액션부터 api 까지이고, 그 액션을 **브라우저가 부르는 배선**은 `web-unit` 이 가짜 SDK로 보는 범위에 남습니다. 그것을 보려면 브라우저가 필요하고 그것은 D-20 이 거절한 것입니다 — 받아들인 비용으로 여기 적습니다.
- **쓰기로 만든 Workflow 를 실행까지 하지 않습니다.** `succeeded` Run 은 R-10 의 고리가 이미 소유합니다.
- `intents/mvp-backlog.md` 의 P5-9 행은 **병합 뒤** PR 번호와 함께 갱신합니다.
