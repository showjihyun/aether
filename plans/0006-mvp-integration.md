spec 이 정한 요구사항(R-1 ~ R-12)·결정(D-1 ~ D-11)은 반복하지 않습니다. 이 문서는 **일곱 단위를 어떤 순서로** 하고, 단위마다 **어느 파일을 누가** 만들며, **무엇으로 판정**하는지를 정합니다. 표기 — **A** 에이전트(`implementer`), **M** 주 세션, **H** 사람(보호 파일·섭외).

이 plan 이 풀어야 하는 문제는 **다섯**입니다.

1. **화면이 데이터 없이 먼저 서지 않게 합니다.** 지금 사이드바는 404 네 개를 가리킵니다 — 껍데기가 먼저 서 있고 내용이 없는 상태가 이미 한 번 일어났습니다. 그래서 **목록 API 와 SDK 가 화면보다 먼저**입니다(MVP-0). 화면 단위는 그것이 끝난 뒤 시작합니다.
2. **계약을 먼저 세웁니다.** CLI 는 제품 코드를 import 하지 않아야 하고(R-2) 그 강제는 `.importlinter` 의 **AR-14** 입니다. 보호 파일이므로 **사람이 먼저 커밋**합니다 — Phase 4 가 AR-13 을 P4-1 앞에 둔 것과 같은 순서입니다. 계약이 먼저 있으면 첫 CLI 코드가 처음부터 위반할 수 없습니다.
3. **`e2e` 단계는 예산 결정과 한 묶음입니다.** spec D-6 이 그 단계를 요구하는데, 더하면 CI 전량이 예산을 넘깁니다(2026-10-17 실측 452,980~605,631 ms / 600,000). 그래서 **`e2e` 를 쓰는 단위(MVP-3·MVP-4)보다 먼저 그 보호 파일 PR 이 가고**, 거기서 사람이 예산을 정합니다. 에이전트는 숫자를 올려 두고 고르지 않습니다(EI-2).
4. **오프라인은 모델 파일이 있어야 판정됩니다.** MVP-3 의 완료 판정이 "네트워크 없이 `succeeded`" 이고 그 전제가 볼륨에 받아 둔 모델입니다(D-5). 그 스크립트와 실패 메시지가 **MVP-3 의 첫 조각**이고, 사람이 한 번 실행해야 그 뒤가 측정됩니다.
5. **TTFSA 는 마지막이고 사람입니다.** MVP-5 는 CLI·화면·오프라인이 전부 끝난 뒤에만 의미가 있습니다(그 전에 재면 "막힌 지점" 이 전부 미구현입니다). 에이전트는 Quickstart 와 양식까지 만들고 **멈춥니다**.

**MVP-0 은 backlog 에 없던 단위입니다.** spec D-3 이 요구하는 목록 API 넷과 SDK 함수를 화면 단위에 섞으면, 화면 PR 하나가 API·SDK·UI 를 한꺼번에 들고 와 리뷰가 불가능해집니다. backlog 에 행을 더하는 것은 **M 이 plan 승인과 같은 커밋에서** 합니다.

**MVP-2 를 셋으로 쪼갭니다**(spec C-3). 목록 → 상세 → 대화 순서이고, 각 단위의 완료 판정은 "실제 데이터로 뜬다" 입니다. 디자인은 최소이고 `apps/web/DESIGN.md` 를 따릅니다.

**Wave 1 과 Wave 2 는 서로 독립이지만 동시에 돌리지 않습니다** — `verify.sh` 의 락이 동시 실행을 막고(`2026-10-03-001`), 두 위임이 번갈아 기다리면 벽시계가 늘어납니다. 그리고 2026-10-17 에 **같은 작업 트리에서 동시 편집이 변경을 잃는 사고**가 한 번 있었습니다(`2026-10-17-001`) — 위임은 **한 번에 하나**입니다.

## 2. 단위별 계획

모든 단위는 **red(실패하는 테스트, 실행해 기록) → green → refactor** 순서입니다. `ModuleNotFoundError` 하나로 여러 단언을 갈음하지 않습니다 — 각 단언이 **자기 이유로** 한 번은 실패하는 것을 보여야 합니다. 단위마다 브랜치 하나, PR 하나, 커밋 trailer `Unit: <단위>`.

### H-2b `harness.config` — `e2e` 단계 (H, **MVP-3 바로 뒤의 별도 PR**)

| 항목 | 내용 |
| --- | --- |
| 왜 뒤로 갔는가 | `harness.config` 10~14행이 **"없는 코드를 검사하는 단계를 미리 적지 않습니다 — verify 가 항상 실패하거나 required 를 내리게 되어 게이트가 죽습니다"** 라고 적고 있습니다. 빈 진입점을 `required=true` 로 등록하면 CI 가 전 PR 에서 빨개지고, exit 0 인 껍데기로 두면 **아무것도 판정하지 않는 초록**이 생깁니다(AGENTS.md Verification 4). 두 길 다 그 규칙이 막는 것입니다 |
| 그래서 언제 | **`scripts/e2e.sh` 가 처음으로 무언가를 단언하는 PR**(MVP-3: 네트워크 끊은 compose 에서 Run 하나가 로컬 모델로 `succeeded`)에서 단계를 등록합니다. 그 PR 은 spec 0006 5절이 이미 "MVP-4 → `e2e`(+ `harness.config`, 사람)" 로 두 번째 사람 손을 예고하고 있습니다 |
| 그동안의 판정 | MVP-3 는 `e2e` 단계 **이전에** 자기 통합 테스트(격리 compose)로 red·green 을 보입니다 — MVP-1 이 같은 방식이었습니다. 단계 등록은 그 테스트를 **게이트에 꽂는** 일이고, 꽂을 것이 있을 때 꽂습니다 |

| 왜 | 지금 `/agents`·`/runs`·`/runs/{id}` 가 **키 없이** `createClient` 를 부릅니다. api 는 `/healthz` 와 문서 경로를 뺀 모든 경로에 `Authorization: Bearer` 를 요구하므로(spec 0001 2.9) 실제 스택에서 세 화면은 **오류 상태**입니다. 타임라인은 그 위에 CORS 도 필요합니다. 즉 **R-5 가 아직 거짓**입니다 |
| 만드는 것 | `apps/web` 서버의 중계 경로. 브라우저는 **same-origin** 으로만 부르고, 키는 **web 컨테이너 안에만** 있습니다(브라우저로 가지 않습니다). SSE 도 같은 길로 흘려야 합니다 — 스트리밍을 버퍼링하지 않는 것이 이 단위의 함정입니다 |
| 사람 손 | **키 주입**(`infra/docker/.env.example` 의 `<generate>` 선례를 따릅니다). 비밀값을 코드·로그·커밋에 남기지 않습니다 |
| 판정 | `web-unit`: 중계 경로가 키를 **붙이고** 브라우저 응답에는 키가 **없다**. SSE 가 청크 단위로 흐른다(모아서 내보내지 않는다). `e2e`(MVP-4): 다섯 경로가 **401 이 아니고** 행을 보여준다 — **R-5 가 여기서 참이 됩니다** |
| 주의 | 중계는 **api 의 계약을 바꾸지 않습니다** — 경로를 그대로 지나가게 합니다. 응답을 손보기 시작하면 web 이 두 번째 API 가 됩니다. 그리고 **키를 브라우저로 내려보내는 변형**(공개 환경변수 등)은 이 결정의 반대입니다 |

### MVP-2c `/knowledge`·`/workflows`·`/settings` 와 Agent 대화 (A)

| 항목 | 내용 |

| 만드는 것 | `app/knowledge/page.tsx`(세트 목록 + 적재 상태), `app/workflows/page.tsx`(정의 목록 + **Run 수준** 실행 목록, D-4), `app/agents/[id]/chat/page.tsx`(대화 — 입력 → `POST /agents/{id}/run` → 스트림), `app/settings/page.tsx`(테마·연결 정보·키 발급 안내 — **D-13**, 사람 2026-10-18) |

## 3. 사람 손

| 순간 | 언제 | 사람이 하는 일 |
| --- | --- | --- |
| **H-1** | MVP-1 **앞** | `.importlinter` 에 AR-14 신설 + AR-5 에 `aether_cli`. `harness-change` 라벨 |
| **H-2a** | MVP-3 **앞** | `harness.config` 에 **예산**(900,000 ms). 선택지 셋과 숫자는 에이전트가 올렸고 사람이 2026-10-17 에 골랐습니다 |
| **H-2b** | MVP-3 **바로 뒤** | `harness.config` 에 `e2e` 단계. 시나리오가 생길 때 꽂습니다(그 파일 10~14행). CC-5 때문에 MVP-3 과 **다른 PR** 입니다(개정 2) |
| **H-3** | MVP-3 중 | 네트워크 있는 환경에서 모델 1회 적재(`scripts/fetch-model.sh`) |
| **H-4** | MVP-5 | **처음 보는 사람 1명의 시간**. 에이전트가 대신할 수 없는 유일한 단위 |

보호 파일 변경은 **셋**입니다(H-1·H-2a·H-2b). 하네스 변경은 한 번에 하나이고 변경 사이에 평가를 실행합니다(CC-1·CC-5) — 그래서 PR 사이에 단위가 들어갑니다(H-1 → MVP-1 → H-2a → MVP-3 → H-2b).

**개정 1 (2026-10-17): H-2 를 H-2a·H-2b 로 쪼갰습니다.** 원래 한 PR 에서 `e2e` 단계와 예산을 같이 정하기로 했는데, `harness.config` 자신이 10~14행에서 "없는 코드를 검사하는 단계를 미리 적지 않습니다 — verify 가 항상 실패하거나 required 를 내리게 되어 게이트가 죽습니다" 라고 금지하고 있었습니다. 예산 결정은 **지금** 급하고(MVP-1 이 `e2e` 없이 626,073 ms 로 이미 넘겼습니다), 단계 등록은 **판정할 것이 생길 때**(MVP-3) 입니다. 2.6 의 D-6 자체는 바뀌지 않습니다 — 순서만 바뀝니다.

**개정 2 (2026-10-18): H-2b 를 MVP-3 과 다른 PR 로 보냈습니다.** 위 표가 "MVP-3 의 PR 과 함께" 라고 적었지만 CC-5 가 "하네스 변경은 제품 코드 변경과 같은 커밋에 섞지 않습니다 — 되돌리기가 한 번으로 끝나게" 라고 정하고 있습니다. `e2e` 단계가 CI 에서 문제를 내면 되돌릴 것은 **그 등록 한 줄**이고, MVP-3 의 제품 코드(worker 의 시작 지점 검사·게이트웨이·compose override)는 그대로 남아야 합니다. 등록 조건("단언할 것이 있을 때")은 그대로 지켜졌습니다 — MVP-3(PR #168)이 먼저 병합됐습니다.

## 4. 판정 절차

`TESTCONTAINERS_RYUK_DISABLED=true ./harness/scripts/verify.sh` 하나가 판정입니다. **H-2b 뒤에는 `e2e` 가 `HARNESS_DEFERRED_STEPS` 에 있으므로 로컬 기본 실행이 그 단계를 미룹니다** — 그 단계에 걸린 단위(MVP-3·MVP-4)는 **`--full` 을 최소 1회** 돌립니다.

**단위마다 보고에 적습니다**: `.harness/verify.json` 의 합계 ms, `api-integration`·(있으면) `e2e` 의 ms. 예산을 넘기면 선택 실패로 집계하고 **사람이 봅니다** — 에이전트가 임계를 올리지 않습니다(EI-2).

| 단위 | 추가 확인(verify 가 아직 못 보는 것) |
| --- | --- |
| MVP-0 | 목록 응답의 페이지 모양이 `GET /agents` 와 **글자까지 같은지** 눈으로 |
| MVP-1 | CLI 를 **설치된 상태로** 한 번(`uv run aether ...` 가 아니라 콘솔 스크립트) |
| MVP-3 | 모델 볼륨을 비운 상태의 오류 메시지를 **읽어 보기**(받는 방법이 적혀 있는지) |
| **MVP-2p** | **api 키 주입** — web 컨테이너가 쓸 키를 발급해 넣습니다(`infra/docker/.env.example` 의 `<generate>` 선례). 비밀값은 커밋하지 않습니다 |
| MVP-2a~2c | 브라우저로 **다섯** 경로를 **직접 열기** 1회(`/settings` 가 D-13 으로 더해졌습니다) |
| MVP-4 | 외부 주소 호출이 실제로 실패하는 것을 로그에서 |
| MVP-5 | 해당 없음 — 측정 자체가 사람 |

**보고에 반드시**: `red 증거`, 판정 명령 exit 표, verify 합계 ms, 미측정, spec/plan 과의 불일치, `docs/` 에 옮길 표 초안.
