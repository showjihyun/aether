# Plans

이 디렉터리는 **승인된 spec 을 파일과 순서로 옮긴 문서**를 담습니다. AI-Native SDLC Playbook 의 `plan.md` 가 이것입니다(출처: [../PROVENANCE.md](../PROVENANCE.md) 6절). intent 가 "무엇을 왜", spec 이 "무엇을 만족해야 하는가" 라면 plan 은 "어느 파일을 어떤 순서로, 무엇으로 판정하며" 입니다. 코드는 plan 뒤에 옵니다.

이 디렉터리는 첫 plan 이 나올 때 만들었습니다. 사슬의 현재 위치는 [../intents/intent.md](../intents/intent.md) 가 소유합니다.

## 파일 이름

```text
plans/<intent 와 같은 번호>-<같은 슬러그>.md
```

intent · spec · plan 이 같은 번호를 가집니다. 세 문서가 짝임을 번호로 찾습니다.

## plan 이 답하는 것과 답하지 않는 것

| 답합니다 | 답하지 않습니다 |
| --- | --- |
| 작업 단위의 실행 순서와 병렬 가능 구간 | 요구사항이 왜 그런가 (spec) |
| 단위마다 만드는 파일·고치는 파일·**사람이 만들어야 하는 파일** | 함수 이름, 코드 |
| 게이트가 켜지기 전후의 판정 명령 | 판정 기준 자체 (spec 의 R-*) |
| 사람 손이 필요한 순간과 그때 무엇을 넘기는가 | 사람이 내릴 결정 (spec 의 D-*) |
| 반복 예산, 중단 조건, 되돌리기 | — |

## 절 구성

| # | 절 | 내용 |
| --- | --- | --- |
| 0 | 머리 표 | 번호, 근거 spec, 상태, 승인 |
| 1 | 순서 | 단위를 wave 로 묶은 실행 순서. 의존 그래프에서 유도하고, 사람 손이 필요한 지점을 표시 |
| 2 | 단위별 계획 | 단위마다 파일 목록(에이전트 / 사람), 안에서의 순서, 판정 명령. 순서는 **red(실패하는 테스트) → green → refactor** 를 가집니다 — 테스트가 성립하지 않는 단위(설정·문서·compose)는 그 사실을 적습니다. 구현 세션의 보고 `red 증거` 가 이 순서를 지켰음을 증명합니다 |
| 3 | 사람 손 | 사람이 개입하는 순간을 한곳에. 각 순간에 에이전트가 무엇을 준비해 넘기는가 |
| 4 | 판정 절차 | 게이트가 켜지기 전과 후에 무엇으로 완료를 판정하는가 |
| 5 | 예산과 중단 | 단위별 반복 예산, 중단 조건, 중단 시 남기는 것, 되돌리기 |
| 6 | Phase 완료 | spec 의 R-* 전부가 어느 단위에서 판정되는가. 끝났을 때 갱신할 문서 |
| 부록 | 보호 파일 제안 | 에이전트가 만들 수 없는 파일의 제안 내용. 사람이 옮겨 만듭니다 |

## 승인

spec 과 같습니다. 사람이 `승인` 행을 채우기 전에는 첫 단위를 시작하지 않습니다. plan 을 승인하는 것은 순서와 사람 손의 횟수에 동의하는 것입니다. 부록의 내용은 제안이며 도구가 거부하면 고쳐서 커밋합니다 — 그것은 개정이 아닙니다.

## 실행 중 갱신

plan 은 실행 중에 바뀌는 문서입니다. 단위를 끝내면 [../intents/mvp-backlog.md](../intents/mvp-backlog.md) 의 `상태` 를 바꾸고(상태는 backlog 가 소유하며 plan 에는 상태 열이 없습니다), 예상과 다른 파일이 생겼으면 plan 의 파일 목록을 고칩니다. 실행이 끝난 plan 은 "무엇을 하려 했는가" 가 아니라 "무엇을 했는가" 의 기록이 됩니다. 처음 승인된 순서와 크게 갈라지면 `개정` 행에 이유를 남깁니다.
