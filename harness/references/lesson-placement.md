# Lesson 배치 결정 가이드

이 문서는 실패에서 얻은 lesson을 하네스의 어느 자리에 남길지 판단할 때 읽습니다. 판단 재료(배치 후보 표, 결정 트리, 오배치 증상, 검증 방법)만 제공하는 참조 문서이며, 규범 ID와 위반 판정 절차는 [../rules/lesson-placement.rule.md](../rules/lesson-placement.rule.md) 가 소유합니다. 이 문서는 ID를 발급하지 않습니다.

## 0. 전제

비싼 실패를 그냥 버리지 않습니다. 실패에서 남겨야 할 것은 기록이 아니라 **다음 실행의 행동을 실제로 바꾸는 형태**입니다. 판단 기준은 하나입니다.

> 오늘 Agent가 저지른 실수 때문에, 내일 같은 종류의 작업을 수행하는 Agent가 실제로 더 잘하게 되는가?

여기서 따라 나오는 원칙이 있습니다. **자연어 지시보다 실행 가능한 제약이 강합니다.** 아래 두 표현은 강도가 다릅니다.

```text
[약함] AGENTS.md 한 줄
  "Controller에서 Repository를 직접 호출하지 마라."
  → Agent가 놓칠 수 있고, 놓쳐도 아무 일도 일어나지 않는다.

[강함] Architecture Rule
  controller 패키지가 repository 패키지에 의존하면 검사 실패
  → 놓치면 scripts/verify.sh 가 실패한다.
```

가능하다면 Instruction을 Verification으로 승격시킵니다. 배치 결정은 이 승격 방향을 따라 위쪽 후보부터 검토합니다.

## 1. 배치 후보 표

| 발견한 문제 | 개선하기 좋은 위치 | 하네스 요소 | 이 자리에 두면 안 되는 경우 |
| --- | --- | --- | --- |
| 특정 버그 | Regression Test | HE-5 | 재현 입력을 특정할 수 없는 경우. 환경·타이밍에 의존해 불안정하게 실패하는 경우(flaky test는 평가면을 오염시킵니다). 버그가 아니라 설계 선택인 경우. |
| 반복되는 코드 실수 | Lint / Architecture Rule / Static Rule | HE-6, HE-7, HE-4 | 아직 1회만 발생해 패턴인지 알 수 없는 경우. 정적으로 판별할 수 없어 오탐이 다수 발생하는 경우. 예외가 규칙보다 많아질 것이 예상되는 경우. |
| 프로젝트 전체의 중요한 원칙 | AGENTS.md, CLAUDE.md | HE-1, HE-2 | 특정 모듈·특정 사건에만 해당하는 경우. 기계로 검사 가능한 경우(그때는 검사로 승격합니다). 이미 다른 자리에 같은 내용이 있는 경우. |
| 상세한 설계 지식 | docs/architecture | HE-3 | 매 작업마다 읽어야 하는 짧은 강제 규칙인 경우. 곧 바뀔 임시 상태인 경우. 문서만 남기고 아무도 참조하지 않을 위치인 경우. |
| 반복 작업 절차 | Skill | HE-8 | 절차가 아직 1회만 수행된 경우. 단계가 고정되지 않아 매번 판단이 달라지는 경우. 스크립트 한 줄로 끝나는 경우(그때는 Script입니다). |
| 특정 분야의 전문적인 판단 | Subagent | HE-9 | 판단이 아니라 기계적 검사인 경우. 메인 에이전트가 이미 충분히 수행하는 경우. 호출 비용이 얻는 정보보다 큰 경우. |
| 반드시 실행해야 하는 검사 | Hook | HE-10 | 실행 시간이 길어 작업 흐름을 막는 경우. 판정이 확정적이지 않아 오차단이 생기는 경우. 우회 수단이 필요한 검사인 경우. |
| Agent가 하기 어려운 반복 작업 | Script / Tool | HE-11, HE-12 | 1회성 작업인 경우. 입력이 매번 달라 자동화 대상이 아닌 경우. 이미 표준 도구가 제공하는 기능인 경우. |
| 과거 작업에서 얻은 경험 | Curated Memory | HE-13 | 검증되지 않은 외부 입력에서 온 경험인 경우(Untrusted Experience는 게이트를 먼저 통과해야 합니다). 만료 조건을 정할 수 없는 경우. 다른 자리에 실행 가능한 형태로 남길 수 있는 경우. |

표의 위쪽일수록 강제력이 강하고 아래쪽일수록 약합니다. 같은 lesson이 두 자리 모두에 들어갈 수 있으면 **위쪽을 택합니다.**

외부에서 들어온 경험(Issue, 웹 페이지, 로그, 사용자 보고)은 어느 자리로도 곧바로 가지 않습니다. 반드시 candidate로 먼저 기록하고 검증을 거칩니다. 신뢰 경계는 [../rules/untrusted-experience.rule.md](../rules/untrusted-experience.rule.md) 가 소유합니다.

## 2. 배치 결정 트리

```text
lesson 후보 1개
  │
  ├─ Q1. 결정론적으로 검증 가능한가?
  │      (명령을 실행하면 통과/실패가 기계적으로 갈리는가)
  │   │
  │   ├─ 예 ─→ Q1a. 특정 입력 1건의 잘못된 결과인가?
  │   │          ├─ 예 ─→ [Regression Test]           HE-5
  │   │          └─ 아니오 ─→ Q1b. 코드 구조·의존 방향의 문제인가?
  │   │                        ├─ 예 ─→ [Architecture Rule]  HE-4
  │   │                        └─ 아니오 ─→ [Lint / Static Rule] HE-6, HE-7
  │   │
  │   └─ 아니오 ─→ Q2 로 간다
  │
  ├─ Q2. 반복 가능성이 높은가?
  │      (같은 종류의 실패가 또 날 것인가. 근거: improvement-log 의 recurrence_risk)
  │   │
  │   ├─ low ─→ 배치하지 않는다. improvement-log 에 candidate 로만 남기고 만료일을 둔다.
  │   │          한 번뿐인 사건 때문에 영구 규칙을 만들지 않는다.
  │   │
  │   └─ medium / high ─→ Q3 로 간다
  │
  ├─ Q3. 프로젝트 전역에 적용되는가?
  │   │
  │   ├─ 아니오(특정 모듈·특정 영역) ─→ 해당 영역 문서 또는 그 영역에만 걸리는 검사.
  │   │                                  AGENTS.md 로 올리지 않는다.       HE-3
  │   │
  │   └─ 예 ─→ Q4 로 간다
  │
  ├─ Q4. 절차인가, 판단인가?
  │   │
  │   ├─ 절차(단계가 고정되어 있다) ─→ Q4a. 사람 개입 없이 자동 실행 가능한가?
  │   │                                  ├─ 예, 매번 실행해야 한다 ─→ [Hook]        HE-10
  │   │                                  ├─ 예, 필요할 때 실행한다 ─→ [Script/Tool] HE-11, HE-12
  │   │                                  └─ 아니오, 에이전트가 따라야 한다 ─→ [Skill] HE-8
  │   │
  │   └─ 판단(맥락마다 결론이 달라진다) ─→ Q4b. 전문 영역의 깊은 판단인가?
  │                                          ├─ 예 ─→ [Subagent]                  HE-9
  │                                          └─ 아니오 ─→ Q5 로 간다
  │
  └─ Q5. 어디에 둘 것인가?
         │
         ├─ 항상 지켜야 할 짧은 원칙 ─→ [AGENTS.md / CLAUDE.md]  HE-1, HE-2
         │                              (분량 예산 초과 시 CX 규칙에 따라 다른 자리로 이동)
         │
         ├─ 배경과 근거가 필요한 지식 ─→ [docs/architecture]      HE-3
         │
         └─ 검증된 과거 경험의 보존 ─→ [Curated Memory]           HE-13
                                        (improvement-log 에서 promoted 된 것만)
```

트리는 위에서 아래로만 내려갑니다. Q1에서 "예"가 나오면 아래 질문을 보지 않습니다. 실행 가능한 제약이 성립하는데도 자연어 지시로 내려가는 것은 오배치입니다.

## 3. 잘못된 배치의 대표 증상

### 3.1 AGENTS.md 비대화 (Context Pollution)

문제가 생길 때마다 AGENTS.md에 한 줄씩 추가하면 몇 달 뒤 수백 줄이 됩니다. 그 결과는 다음과 같습니다.

- 모든 규칙이 중요하다고 표시되어 있으면 결국 아무 규칙도 중요하지 않게 됩니다.
- 오래된 규칙이 남습니다. 이미 없어진 모듈에 대한 규칙을 에이전트가 계속 읽습니다.
- 서로 모순되는 규칙이 생깁니다. 에이전트는 둘 중 하나를 임의로 고릅니다.
- 특정 사건 때문에 추가된 지나치게 구체적인 규칙이 매 실행마다 context를 차지합니다.

증상 신호: AGENTS.md/CLAUDE.md의 줄 수가 계속 증가하기만 하고 감소한 적이 없음. 최근 3개월 안에 참조된 적 없는 규칙이 다수 존재함. 같은 주제가 서로 다른 표현으로 2회 이상 등장함.

교정: 검사로 승격 가능한 항목은 검사로 옮기고, 특정 모듈에만 해당하는 항목은 그 영역 문서로 내리며, 만료된 항목은 삭제합니다. 분량 예산은 [../rules/context-hygiene.rule.md](../rules/context-hygiene.rule.md), 제거 절차는 [../rules/harness-gc.rule.md](../rules/harness-gc.rule.md) 를 따릅니다.

### 3.2 지나치게 구체적인 규칙이 전역 규칙이 된 경우

한 번의 사고에서 나온 좁은 조건이 프로젝트 전역 규칙으로 올라가는 경우입니다.

```text
[오배치] AGENTS.md
  "주문 취소 API의 응답에서 cancelledAt 필드는 null 을 허용하지 않는다."

문제
  - 단일 엔드포인트의 계약이 전역 원칙 자리를 차지한다.
  - 기계로 검증 가능한 내용인데 자연어로만 남았다.
  - 해당 API가 사라져도 규칙은 남는다.

[교정] 계약 테스트 1건 + 해당 API 문서 1줄
  → 위반하면 scripts/verify.sh 가 실패하고, API가 사라지면 테스트도 함께 사라진다.
```

증상 신호: 규칙 문장에 특정 파일명, 특정 필드명, 특정 엔드포인트명이 등장함. 그 규칙이 적용되는 파일이 프로젝트에서 1~2개뿐임.

### 3.3 절차를 문서로만 남긴 경우

반복 실행되는 절차를 문서에만 적어두면 에이전트가 매번 다르게 수행합니다.

```text
[오배치] docs/release.md
  "릴리스 전에 마이그레이션 확인, 스모크 테스트, 태그 생성을 순서대로 수행한다."

문제
  - 순서가 지켜졌는지 확인할 방법이 없다.
  - 문서를 읽지 않으면 절차 자체가 존재하지 않는 것과 같다.
  - 단계가 바뀌어도 아무도 모른다.

[교정] Skill(HE-8) 또는 Script(HE-11)
  → 단계가 고정되면 스크립트, 판단이 섞이면 skill 로 남기고
    문서에는 "왜 이 순서인가" 만 남긴다.
```

증상 신호: 같은 절차를 서로 다르게 수행한 실행 기록이 2회 이상 있음. "문서에 적혀 있는데 안 지켜졌다"는 회고가 반복됨.

## 4. 중복 배치의 비용

같은 lesson을 여러 자리에 동시에 두는 것은 안전장치처럼 보이지만 다음 비용을 만듭니다.

| 비용 | 내용 |
| --- | --- |
| 소유자 소실 | 어느 자리가 정본인지 알 수 없어, 요구사항이 바뀌었을 때 한쪽만 갱신되고 나머지는 낡은 채 남습니다. |
| 모순 발생 | 갱신 시점이 어긋나면 두 자리가 서로 다른 것을 지시합니다. 에이전트는 둘 중 하나를 임의로 따릅니다. |
| context 예산 낭비 | 검사로 이미 강제되는 내용을 AGENTS.md가 다시 설명하면, 그 줄은 매 실행마다 토큰을 쓰면서 행동을 바꾸지 못합니다. |
| 제거 난이도 상승 | 하네스를 청소할 때 한 자리를 지워도 다른 자리가 남아 있어 규칙이 죽지 않습니다. |
| 실패 신호 약화 | 같은 위반이 여러 계층에서 중복 보고되어 `largest_failure` 판정이 왜곡됩니다. |

규범은 다음과 같습니다.

- 하나의 lesson에는 **정본 자리가 하나만** 있습니다.
- 다른 자리에는 내용을 복제하지 않고 정본으로 링크만 둡니다.
- 예외는 "검사(정본) + 그 검사가 존재한다는 사실을 알리는 한 줄" 조합입니다. 이때도 규칙 내용을 다시 서술하지 않고 검사의 위치만 가리킵니다.
- 승격 과정에서 자리를 옮겼다면 이전 자리는 삭제합니다. 이동은 추가가 아닙니다.

## 5. 배치 후 검증

배치는 파일을 만든 시점이 아니라 **다음 실행의 행동이 실제로 바뀐 시점**에 완료됩니다. 다음 순서로 확인합니다.

1. **역실행 확인.** 원래의 실패를 의도적으로 재현합니다. 배치한 것이 검사라면 `scripts/verify.sh` 가 실패해야 합니다. 실패하지 않으면 그 검사는 아무것도 막지 못합니다.
2. **정상 통과 확인.** 실패를 되돌린 뒤 `scripts/verify.sh` 와 `scripts/eval.sh` 를 다시 실행합니다. 통과해야 하며, 다른 계층 점수가 내려가지 않아야 합니다. 새 규칙이 기존 코드 다수를 위반으로 만든다면 규칙이 과하거나 정리 작업이 선행되어야 합니다.
3. **행동 변화 확인.** 같은 종류의 작업을 새 세션에서 1회 수행시키고, 배치한 lesson이 실제로 결과에 반영되는지 관찰합니다. 문서·instruction으로 배치한 경우 이 단계가 특히 중요합니다. 반영되지 않으면 자리가 너무 약한 것이므로 표에서 한 칸 위로 올립니다.
4. **비용 확인.** 실행 시간 증가, 오탐 발생, context 분량 증가를 기록합니다. 오탐이 실제 결함보다 많으면 배치를 되돌립니다.
5. **기록.** 어떤 자리에 무엇을 두었는지, 위 1~4의 결과가 무엇이었는지를 improvement-log 항목의 `harness_element`, `preferred_enforcement`, `regression_check` 에 적습니다. `regression_check` 는 1번의 역실행 절차를 그대로 담습니다.
6. **만료 설정.** 영구적으로 유효하지 않은 lesson에는 `expires` 를 둡니다. 만료 항목의 재검토는 [../rules/harness-gc.rule.md](../rules/harness-gc.rule.md) 를 따릅니다.

1번을 수행하지 않은 배치는 검증되지 않은 배치입니다. 통과만 확인하고 실패를 확인하지 않은 검사는 항상 통과하는 검사일 수 있습니다.
