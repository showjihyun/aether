# 성숙도 단계 (L0~L5)

이 문서는 지금 이 프로젝트가 self-improving loop의 어느 단계에 있는지 판정하고, 다음 단계로 가기 위해 무엇을 추가할지 정하는 기준입니다. 하네스를 처음 도입할 때, 개선안의 우선순위를 다툴 때, "이 구조를 지금 만들어도 되는가"를 결정할 때 읽습니다. 단계 이름과 특징은 원문 표를 그대로 유지하며 임의로 늘리거나 줄이지 않습니다.

## 1. 정본 단계표

| 단계 | 특징 |
| --- | --- |
| L0 Prompting | 사람이 계속 다음 작업을 지시한다 |
| L1 Agent Loop | Agent가 Code → Test → Fix를 반복한다 |
| L2 Eval Loop | 명시적인 Goal과 Evaluation을 기준으로 반복한다 |
| L3 Persistent Learning | 실패가 Test, Docs, Skill, Tool로 남는다 |
| L4 Harness Loop | 작업 기록을 분석해서 Harness 개선안을 만든다 |
| L5 Self-Evolving Harness | Candidate Harness를 평가하고 자동으로 Promote/Reject한다 |

단계는 누적입니다. 상위 단계는 하위 단계를 전제로 하며, 하위 단계를 건너뛴 상위 구조는 단계 달성으로 인정하지 않습니다.

## 2. 판정 방법

각 단계의 체크리스트 항목은 모두 예/아니오로 답할 수 있어야 합니다. 판정은 의견이 아니라 관측으로 합니다. "그렇게 하고 있다"가 아니라 "이 파일이 있다", "이 명령이 0으로 끝난다", "이 로그에 항목이 있다"로 답합니다.

- 어떤 단계의 체크리스트 항목이 **모두 예**일 때만 그 단계에 도달한 것으로 봅니다.
- 하나라도 아니오이면 그 단계에 도달하지 않은 것이며, 현재 단계는 모든 항목이 예인 가장 높은 단계입니다.
- 판정 결과는 improvement log 또는 하네스 도입 기록에 날짜와 함께 남깁니다.

## 3. 단계별 판정 기준

### L0 Prompting

**체크리스트**

| ID | 판정 항목 (예/아니오) |
| --- | --- |
| L0-C1 | 에이전트를 사용해 실제 저장소의 코드를 변경한 적이 있는가? |
| L0-C2 | 작업 지시가 사람의 매 턴 입력으로 이루어지는가? |

**전형적 증상**

- 사람이 "테스트해봐", "이 에러 고쳐", "리뷰 반영해"를 순서대로 입력합니다. 사람이 사실상 workflow engine입니다.
- 같은 설명을 매번 반복해서 붙여넣습니다.
- 에이전트가 어떤 명령으로 검증해야 하는지 모릅니다.

**다음 단계로 가기 위해 추가할 요소**

- HE-1 AGENTS.md 또는 HE-2 CLAUDE.md — 최소한의 지도 한 장.
- HE-11 scripts — 통합된 검증 명령 하나(`scripts/verify.sh`).

### L1 Agent Loop

**체크리스트**

| ID | 판정 항목 (예/아니오) |
| --- | --- |
| L1-C1 | 통합된 검증 명령이 하나 있고, 저장소 루트에서 한 줄로 실행되는가? |
| L1-C2 | 그 명령이 성공·실패를 종료 코드로 구분하는가? |
| L1-C3 | 에이전트가 사람의 추가 지시 없이 실패를 읽고 수정을 시도하는가? |
| L1-C4 | AGENTS.md 또는 CLAUDE.md에 "완료 선언 전에 검증 명령을 실행한다"가 적혀 있는가? |

**전형적 증상**

- 에이전트가 스스로 반복하지만, 100번 반복해도 101번째 실행이 1번째보다 나은 상태에서 시작하지 않습니다.
- 어제 지적한 실수를 오늘 다시 저지릅니다. 현재 작업은 개선되지만 작업 시스템은 개선되지 않습니다.
- 검증이 "테스트 통과"에만 걸려 있고 아키텍처·lint·정적 분석은 사람이 눈으로 봅니다.

**다음 단계로 가기 위해 추가할 요소**

- HE-14 evaluation — 목표와 판정 기준을 명시적인 산출물로 만듭니다(`scripts/eval.sh`, `.harness/latest-eval.json`).
- HE-5 tests, HE-6 lint rules, HE-7 static analysis — 검증 명령의 단계를 layer별로 채웁니다.
- HE-15 workflow — 예산과 종료 조건을 정합니다.

### L2 Eval Loop

**체크리스트**

| ID | 판정 항목 (예/아니오) |
| --- | --- |
| L2-C1 | 목표가 자연어 대화가 아니라 파일에 적힌 판정 기준으로 존재하는가? |
| L2-C2 | 평가가 단일 숫자가 아니라 2개 이상의 layer로 나뉘어 있는가? |
| L2-C3 | 평가 결과가 기계 판독 가능한 파일(`.harness/latest-eval.json`)로 남는가? |
| L2-C4 | 임계값과 통과·실패 판정이 사람의 해석 없이 결정되는가? |
| L2-C5 | 반복에 최대 횟수와 중단 조건이 정해져 있는가? |
| L2-C6 | 평가 기준 자체를 에이전트가 수정하지 못하도록 막는 규칙이 있는가? |

**전형적 증상**

- 점수는 올라가는데 제품이 좋아졌다는 확신이 없습니다. 의미 없는 테스트로 커버리지가 오르거나 lint 규칙이 꺼져 있습니다.
- 반복이 끝나지 않거나, 같은 실패를 계속 다른 방식으로 우회합니다.
- 작업이 끝나면 그 작업에서 배운 것이 세션과 함께 사라집니다.

**다음 단계로 가기 위해 추가할 요소**

- HE-13 memory — improvement log를 만듭니다. 단, `status: candidate` 로 시작합니다.
- HE-3 documentation, HE-4 architecture rules — 반복된 실수를 문서와 기계 판정 규칙으로 옮깁니다.
- HE-8 skills — 반복되는 작업 절차를 절차 산출물로 분리합니다.

### L3 Persistent Learning

**체크리스트**

| ID | 판정 항목 (예/아니오) |
| --- | --- |
| L3-C1 | 최근 실패 중 최소 하나가 test, lint·arch-rule, doc, skill, tool 중 하나로 저장소에 남았는가? |
| L3-C2 | 그 산출물이 git에 커밋되어 리뷰를 거쳤는가? |
| L3-C3 | improvement log에 `status` 필드가 있고 `candidate` 와 `promoted` 가 구분되는가? |
| L3-C4 | 승격되지 않은 lesson이 AGENTS.md·CLAUDE.md에 직접 기록되지 않는가? |
| L3-C5 | 외부 입력(issue, 로그, 웹 문서, 사용자 보고)이 검증 없이 영구 규칙이 되지 않도록 하는 경계가 있는가? |
| L3-C6 | 남긴 lesson이 실제로 다음 작업의 행동을 바꾸는 형태인가(읽히지 않아도 실패로 드러나는가)? |

**전형적 증상**

- lesson은 남는데 남는 자리가 대부분 AGENTS.md입니다. 몇 달 뒤 수백 줄이 되고 모든 규칙이 중요해집니다.
- 한 번 발생한 사건 때문에 지나치게 구체적인 규칙("Never use asynchronous processing.")이 영구화됩니다.
- 무엇이 왜 추가되었는지 근거를 되짚을 수 없습니다.

**다음 단계로 가기 위해 추가할 요소**

- HE-9 subagents — 작업 기록을 분석해 개선안을 만드는 역할을 구현 역할과 분리합니다.
- HE-8 skills — 회고 절차(harness retrospective)를 skill로 고정합니다.
- HE-12 tools — improvement log를 다루는 CLI를 만듭니다.
- HE-10 hooks — 반드시 실행되어야 하는 검사를 hook으로 올립니다.

### L4 Harness Loop

**체크리스트**

| ID | 판정 항목 (예/아니오) |
| --- | --- |
| L4-C1 | 작업 종료 시 회고를 수행하는 정해진 절차가 산출물로 존재하는가? |
| L4-C2 | 회고가 근거(로그, 실패 메시지, 수정 이력)와 함께 개선안을 산출하는가? |
| L4-C3 | 개선안을 만드는 주체가 제품 코드를 만드는 주체와 분리되어 있는가? |
| L4-C4 | 하네스 변경이 한 번에 하나씩 적용되고, 변경 전후 평가 점수가 비교되는가? |
| L4-C5 | 새로 추가한 규칙·skill이 representative task와 held-out task로 회귀 검증되는가? |
| L4-C6 | 낡은 규칙·문서·skill을 주기적으로 제거하는 절차가 있는가? |
| L4-C7 | 승격 판단에 사람의 승인이 개입하는 지점이 명시되어 있는가? |

**전형적 증상**

- 개선안은 쌓이는데 무엇이 점수를 올렸는지 알 수 없습니다. 한 번에 여러 개를 바꿨기 때문입니다.
- 규칙이 계속 늘기만 하고 줄지 않습니다. 옛 workaround가 영원히 남습니다.
- 회귀 검증 없이 적용한 규칙이 다른 작업을 망가뜨립니다. self-improvement가 아니라 self-drift입니다.

**다음 단계로 가기 위해 추가할 요소**

- HE-14 evaluation — held-out task를 별도로 관리하고 평가 무결성 규칙을 강화합니다.
- HE-15 workflow — 승격·기각 판정을 자동화하기 위한 상태 전이를 정의합니다.
- HE-11 scripts — 후보 하네스를 적용·되돌리는 절차를 스크립트로 만듭니다.

### L5 Self-Evolving Harness

**체크리스트**

| ID | 판정 항목 (예/아니오) |
| --- | --- |
| L5-C1 | L4의 모든 항목이 예인가? |
| L5-C2 | 후보 하네스를 적용한 상태와 적용하지 않은 상태를 자동으로 비교할 수 있는가? |
| L5-C3 | 승격·기각이 사람의 판단 없이 평가 결과만으로 결정되는가? |
| L5-C4 | 기각된 후보가 자동으로 원복되고 그 사실이 기록되는가? |
| L5-C5 | held-out task가 승격 판정에 사용되지 않고 검증에만 사용되는가(평가 오염 방지)? |
| L5-C6 | 자동 승격에서 제외되는 영역(보안 민감 변경 등)이 명시되어 있는가? |

**전형적 증상 (도달했을 때)**

- 하네스 변경 이력이 평가 점수 변화와 함께 자동으로 축적됩니다.
- 사람은 개별 규칙이 아니라 평가 기준과 제외 영역을 관리합니다.

## 4. 규범: L5부터 만들지 않습니다

원문의 권고를 이 번들의 규범으로 채택합니다.

- **L5부터 만들지 않습니다. L3와 L4를 제대로 만듭니다.** 실제 개발을 진행하는 팀에게 필요한 것은 자동 진화가 아니라 실패가 시스템에 남는 구조입니다.
- 시작 순서는 다음 세 가지입니다. 이 셋만으로도 에이전트를 사용하는 방식이 달라집니다.

```text
1. 통합된 Verify 명령

2. Improvement Log

3. Harness Retrospective
```

- 처음부터 multi-agent system, vector database, 자동 skill generator를 만들지 않습니다. 이들은 L3·L4의 결핍을 메우지 못하며, 결핍을 감춥니다.
- 한 번에 한 단계씩 올라갑니다. 단계를 건너뛴 도입은 도입한 구조가 아니라 건너뛴 단계의 부재로 실패합니다.

## 5. 안티패턴

| ID | 안티패턴 | 왜 실패하는가 | 교정 |
| --- | --- | --- | --- |
| AP-1 | L2 이하에서 자동 promote/reject(L5 구조)를 도입합니다. | 승격·기각을 판정할 평가가 아직 신뢰할 만하지 않습니다. 잘못된 평가로 자동 승격하면 오염된 규칙이 사람 검토 없이 영구화됩니다. | 자동 판정을 끄고, 먼저 L2-C2·L2-C3·L2-C6을 만족시킵니다. 승격은 사람 승인으로 둡니다. |
| AP-2 | L1에서 improvement log부터 만듭니다. | 평가 없이 memory부터 만들면 잘못 판단했던 경험까지 정확히 보존됩니다. | 먼저 검증 명령과 평가 layer를 만들고, 그 근거 위에서 후보를 기록합니다. |
| AP-3 | L3를 AGENTS.md 한 파일로만 달성했다고 판정합니다. | 지시문은 놓쳐도 실패로 드러나지 않습니다. L3-C6을 만족하지 못합니다. | 반복되는 코드 실수는 lint·arch-rule로, 특정 버그는 회귀 테스트로 옮깁니다. |
| AP-4 | 회귀 검증 없이 후보 하네스를 즉시 적용합니다. | 현재 task 하나에 과적합된 규칙이 프로젝트 전체를 망가뜨립니다. | representative task와 held-out task로 검증한 뒤에만 적용합니다. |
| AP-5 | 한 번에 여러 하네스 요소를 동시에 바꿉니다. | 점수가 올라도 무엇 때문인지 알 수 없어 다음 판단의 근거가 남지 않습니다. | 변경을 하나씩 분리하고 각 변경마다 평가를 돌립니다. |
| AP-6 | 추가만 하고 제거하지 않습니다. | 규칙은 낡고 문서는 코드와 어긋납니다. context만 소모하고 강제력은 줄어듭니다. | 주기적 정리 절차를 두고 만료된 항목을 제거합니다. |
